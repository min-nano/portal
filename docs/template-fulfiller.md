# 雛形記入ユニット（template-fulfiller）

現況検査レポート・構造計算安全証明書・必要壁量 計算ツールの 3 つは、
それぞれ別のツールとして作ってきました。しかし 3 つとも

> **雛形を手に入れ、入力を書き込み、生成物を渡す**

という同じ流れをしています。違うのは流れそのものではなく、**雛形が
どこにあるか・入力がどんな形か・どこへどう書き込むか・生成物をどう渡すか**
という、その流れに渡すパラメータだけです。

そこで、この 3 つを 1 つずつ別リポジトリへ出す（[plugin-architecture.md](plugin-architecture.md)
§9 の第 3・4 段）のをやめ、**流れを 1 つの実装にまとめ、3 つのツールは
そこへ渡す記述（レシピ）にする** 形にします。この文書は、その分け方・
レシピの語彙・エンジンの契約・移行の順序をまとめたものです。

## これは 2 つの別々の決定です

この文書を書く途中で分かったことなので、先に書いておきます。

| | 得られるもの | 費用 | 今回 |
| --- | --- | --- | --- |
| **統一** 3 実装 → 1 エンジン + 3 レシピ | 重複の解消。**この提案の価値のほぼ全部** | 新しくフレームワークを作るリスク | **やる** |
| **分割** そのエンジンを別リポジトリへ | 版の固定・CI の分離・読み込み量 | 語彙を変えるたびにリポジトリを跨ぐ往復 | **保留** |

**統一は portal の中だけで完結します。分割しなくても価値は全部取れます。**

そして分割は今やるべきではありません。版の壁の向こうに置いてよいのは
**落ち着いたもの**で、生まれたてのフレームワークはこれから最も変わるもの
だからです。4 つめの雛形記入型ツールが来れば語彙はほぼ確実に動きます。
そのたびに版上げ PR が要るというのは、plugin-architecture.md §8 が
「払うもの」に挙げた費用そのものです。

**エンジンの切り出しは、語彙が動かなくなってから判断します。**
`min-nano/portal-tool-template-fulfiller` は受け皿として作ってありますが、
中身は空のままにしておきます。分割の機構（タグ → 版の固定 → 取り込み）を
先に試すなら、**変わらないもの**——`xlsx_fill.py`（495 行）・`pdf_tools.py`
（347 行）・`pdf_write.py`（488 行）という、app への import が 1 つも無い
純粋なライブラリ——のほうが適しています。

## 1. 3 つが同じ流れであることの確認

```
⓪ 記述を配る ───→ 画面がフォームを組み立てる
①  雛形を手に入れる
②  入力を正規化し、確かめる
③  雛形へ記入する
④  生成物を渡す
⑤ （生成物を読み戻してフォームへ戻す）      ← 安全証明書だけ
```

この 5 段に、3 つのツールを並べたものが次の表です。**行が流れ、
セルの中身がパラメータ**になっています。

| | ① 雛形 | ② 入力の構造 | ③ 記入 | ④ 引き渡し | ⑤ 読み戻し |
| --- | --- | --- | --- | --- | --- |
| 現況検査レポート | Drive の .xlsx（共有設定に「フォルダ + ファイル名」） | 繰り返し（部屋 × 計測点） | セル | ダウンロード | — |
| 構造計算安全証明書 | Drive の Google ドキュメント（同上） | 平らな記入欄 + 選択肢（前提が連鎖する） | プレースホルダー置換 → PDF 書き出し → 印 | Drive へ保存（上書き / 別名） | あり |
| 必要壁量 計算 | リポジトリ同梱の配布物 .xlsx | 入れ子の節（開閉・連動プルダウン） | セル + チェックボックス | ダウンロード | — |

セルの中身は 2 種類しかありません。

* **段取り**（どうやるか）… 「Drive の共有設定から雛形を取る」「条件の外れた
  欄は空にしてから書く」「ダウンロードで返す」といった、**流れの運び方**。
  数は少なく、ツールが増えても増えない
* **記述**（何を、どこへ）… 計測点の一覧、セル参照、プレースホルダー名、
  選択肢、条件。**ツールごとに全部違い、量はこちらが圧倒的に多い**
  （今の 3 つの mapping で 148 kB）

**段取りを切り出し、記述を portal に残す。** これがこの設計です
（段取りが使う道具——xlsx エディタや PDF ライター——は、これまでどおり
土台に置きます。§2）。

---

## 2. 分け方

分割を保留したので、当面はすべて portal の中にあります。**ただし置き場所は
分けます**——将来ここに線を引いて切り離せるように、そして何より
「段取り」と「記述」と「道具」が混ざらないようにするためです。

```
  backend/app/
    template_fulfiller/          流れと段取り（＝将来のユニット）
      recipe.py                    レシピの読み込みと検証
      form.py                      面・節・かたまり・入力欄の走査、条件の評価
      normalize.py                 入力の正規化
      fill_xlsx.py                 セル・チェックボックスへの記入
      fill_doc.py                  プレースホルダー置換・PDF への印
      deliver.py                   ダウンロード / Drive への保存
      routes.py                    レシピからルートを生やす

    tools/                       記述（ツールごと）
      excel-report-formatter/recipe.json
      structural-cert-formatter/recipe.json
      wall-quantity-calculator/recipe.json ＋ templates/

    xlsx_fill.py  pdf_tools.py  pdf_write.py  google_docs.py
                                 道具（土台。ユニットへは持って行かない）
```

この形なら、切り離すと決めたときに動かすのは `template_fulfiller/` だけに
なります。逆に切り離さないと決めても、混ざらないという利得は残ります。

### 3 者が何を持つか

template-fulfiller は、ツールと同じく **`portal_sdk`（土台）の上に乗ります**。
土台とツールの間に 1 枚挟まる位置づけで、
[plugin-architecture.md](plugin-architecture.md) §4 の 3 つの継ぎ目は
そのまま生きています。したがって持ち物は 3 者に分かれます。

| | portal（記述） | template-fulfiller（流れと段取り） | 土台 `portal_sdk`（道具） |
| --- | --- | --- | --- |
| **雛形** | 同梱物そのもの・その出所（`source.json`）・Drive 雛形の種類 | 同梱物の読み込み、「フォルダ + ファイル名」からの最新版の取得、雛形設定の API（Picker で選ばれたファイルの確認と保存） | 代理アクセス（Drive / Docs）、共有設定 |
| **入力** | 面・節・かたまり・入力欄・選択肢・条件（＝レシピ） | レシピの解釈、正規化、条件の評価（前提の連鎖を含む）、必須の確認、選べない値の拒否 | 認証、エラーの返し方 |
| **記入** | 書き込み先（セル・プレースホルダー・印の位置・チェックボックス） | どの書き込み先をどの順で使うか、置換表の組み立て、印の位置決め、置換されなかった欄の警告 | xlsx エディタ（`xlsx_fill`）、PDF ライター（`pdf_write` / `pdf_tools`）、Docs の一括置換 |
| **引き渡し** | ファイル名の作り方、ルートの名前（`/reports` など） | ダウンロードの応答、ファイル名の組み立て | 「保存 / 別名で保存」の保存先の解決と書き込み |
| **読み戻し** | 解析ルール（正規表現・ラベルの右）・文書情報のキー | ルールの適用、印が付いているかの判定、文書情報からの復元 | PDF のレイアウト読み取り（`pdf_tools`） |
| **計算** | どの wasm のどの op か | 画面の値とサーバの値の突き合わせ | wasm の実行と配布 |

> **なぜ道具は土台に残すのか。** `pdf_tools.py` は安全証明書だけでなく
> **面材張り大壁 計算ツール（このユニットに入らない）も使っています**。
> このユニットへ持って行くと、面材張り大壁がこのユニットに依存するか、
> 同じものが 2 つになります。`xlsx_fill.py` と `pdf_write.py` も同じ理由で、
> plugin-architecture.md §4.2 が最初から「xlsx エディタ・PDF ライターは
> 土台」としているとおりに置きます。
>
> **道具と段取りの線引き**はこうです——「xlsx のこのセルを壊さずに書き換える」
> は道具、「レシピのどの欄がどのセルに対応し、どれを空にするか」が段取りです。

## 3. レシピの語彙

この設計の核心です。**3 つのツールの mapping が、1 つの語彙で書けること**が
成り立たなければ、この分け方は成立しません。以下は今ある 3 つの mapping を
読んで導いたもので、無理な一般化ではなく実際に重なっている部分です（§4 に
突き合わせを載せます）。

レシピは 1 枚の JSON です。

```jsonc
{
  "id": "wall-quantity-calculator",
  "name": "小規模木造建築物 必要壁量 計算ツール",

  "template": { … },   // ① 雛形の在り処
  "form":     { … },   // ② 入力の構造
  "deliver":  { … },   // ④ 引き渡し
  "read_back":{ … },   // ⑤ 読み戻し（任意）
  "verify":   { … }    //   計算との突き合わせ（任意）
}
```

③ の記入は独立した節を持ちません。**書き込み先は入力欄そのものが持つ**ためです
（§3.5）。

### 3.1 入力の構造 — 4 つの階層

```
面 (surface)          同じフォームの別版。書き込み先の宛先（シート）が変わる
  節 (section)        画面の見出し。任意で「使う / 使わない」の入り切りを持つ
    かたまり (block)  単発 / 繰り返し
      入力欄 (field)  key・ラベル・型・条件・書き込み先
```

* **面** は省略できます。省略すると面が 1 つだけあるものとして扱います。
  必要壁量の「平屋建て / 2 階建て」だけがこれを使い、面ごとに書き込み先の
  シートが変わります
* **節** は `key`・`title`・`note` と、任意の `toggle`（その節を使うかの
  入り切り。切なら中の欄は書き込まない）を持ちます
* **かたまり** は 2 態だけです

### 3.2 かたまり — 単発と繰り返し

```jsonc
// 単発。入力欄が並ぶだけで、それぞれが自分の書き込み先を持つ。
{ "kind": "fields",
  "fields": [ { "key": "property_name", "label": "物件名", "type": "text",
                "target": { "cell": "K4" } } ] }

// 繰り返し。「1 つ分の形」と「インスタンスの並び」で書く。
{ "kind": "repeat",
  "key": "ceiling_custom",
  "label": "天井(屋根)断熱材の任意入力",
  "columns": ["", "該当面積(m²)", "密度(kg/m³)", "厚さ(mm)"],
  "visible_when": { "field": "ceiling_insulation", "in": ["任意入力"] },
  "instances": [ { "key": "1", "label": "仕様①", "origin": 33 },
                 { "key": "2", "label": "仕様②", "origin": 34 } ],
  "fields": [ { "key": "area",      "label": "該当面積", "type": "number",
                "target": { "column": "O" } },
              { "key": "density",   "label": "密度",     "type": "number",
                "target": { "column": "R" } },
              { "key": "thickness", "label": "厚さ",     "type": "number",
                "target": { "column": "U" } } ] }
```

**繰り返しの書き込み先は「列（1 つ分の形が持つ）＋ 行（インスタンスが持つ）」で
決まります。** 今の 3 つの mapping がこれで書けることは実データで確かめてあります:

* 必要壁量の表ブロック **13 個すべて**が「全行で列がそろい、1 行 = 1 インスタンス」
* 繰り返しの中の入力欄 **83 個すべて**が `<インスタンスの key>_<欄の key>` という
  key を持っている（＝すでに「1 つ分の形 × インスタンス」で書かれている）
* 現況検査レポートの部屋も同じ形（`block_start_rows` がインスタンスの起点、
  `row_offset` と `col` が 1 つ分の形）

繰り返しは**入れ子にでき、行の起点は足し合わされます**。現況検査レポートの
「部屋 × 計測点」がこれにあたります。

```jsonc
{ "kind": "repeat", "key": "rooms", "label": "部屋",
  // 利用者が増やす繰り返し。並べた数がそのまま上限になる。
  "added_by_user": true,
  "instances": [ { "origin": 29 }, { "origin": 43 }, … { "origin": 150 } ],
  "fields": [ { "key": "floor",     "label": "階数",   "type": "number",
                "target": { "column": "E" } },
              { "key": "room_name", "label": "部屋名", "type": "text",
                "target": { "column": "G" } } ],
  "blocks": [
    { "kind": "repeat", "key": "measurements",
      "instances": [ { "key": "floor_x", "label": "X方向", "group": "床", "origin": 0 },
                     { "key": "floor_y", "label": "Y方向", "group": "床", "origin": 1 }, … ],
      "fields": [ { "key": "select",   "type": "select", "target": { "column": "S" },
                    "options": ["←", "→", "傾斜無"] },
                  { "key": "diff",     "type": "number", "target": { "column": "AC" } },
                  { "key": "distance", "type": "number", "target": { "column": "AG" } },
                  { "key": "digital_level", "type": "number", "target": { "column": "V" } } ] } ] }
```

`added_by_user` が **決め打ちの表**（必要壁量）と**利用者が増やす繰り返し**
（現況検査レポート）を分ける唯一の印です。書き込み先の決まり方は同じで、
違うのは「インスタンスをいくつ使うか」を誰が決めるかだけです。

### 3.3 入力欄

```jsonc
{ "key":   "snow_depth",
  "label": "垂直積雪量",
  "type":  "number",              // text | number | select | date | checkbox
  "unit":  "cm", "step": "1", "min": 0,
  "note":  "解説・注意事項の表1-3を必ず参照する。",
  "visible_when":  { "field": "heavy_snow", "in": ["あり(多雪区域)"] },
  "required_when": { "field": "heavy_snow", "in": ["あり(多雪区域)"] },
  "target": { "cell": "H20" } }
```

### 3.4 条件

述語は 3 つだけです。

| 条件 | 意味 |
| --- | --- |
| `visible_when` | 満たさないとき、その欄（かたまり・節）は**無い**。画面に出さず、雛形にも書かない（空にする） |
| `required_when` | 満たすとき必須になる（`required: true` は無条件の必須） |
| `fixed_when` | 満たすとき、入力によらず決め打ちの値を書く |

述語の中身は `{ "field": …, "in": […] }` / `{ … , "not_in": […] }` /
`{ … , "filled": true }` の 3 通り。

**前提は連鎖します。** 「プログラムの名称 → 大臣の認定 → 認定番号」のように、
ある欄が消えたことで別の欄の前提も外れることがあるため、条件の評価は
**変化が無くなるまで繰り返します**（今 `structural_cert.py` の
`_clear_inactive` が行っていることを、エンジンが全ツールに対して行う）。

> **今ある 2 つの仕掛けがここへ畳まれます。** 安全証明書の
> `depends_on_field`（記入欄が埋まっているときだけ選ばせる）は
> `visible_when: { field: …, filled: true }` に、`requires_field`
> （その選択肢を選んだときだけ意味を持つ欄）は選ばれる側の欄の
> `visible_when: { field: …, in: [値] }` になります。専用の仕掛けが
> 2 つ消え、必要壁量がすでに持っている条件と同じものになります。

### 3.5 書き込み先 — 欄に付くものと、選択肢に付くもの

書き込み先は 2 系統あります。

**欄そのものに付くもの**（入力した値がそこへ入る）

| `target` | 使う機構 |
| --- | --- |
| `{ "cell": "H20" }` | xlsx のそのセルだけを書き換える |
| `{ "column": "AC" }` | 繰り返しの中。行はインスタンスの起点から決まる |
| `{ "placeholder": ["{{年号年}}"] }` | Google ドキュメントの一括置換 |

**選択肢ごとに付くもの**（選ばれたものだけが印される）

| `target` | 使う機構 |
| --- | --- |
| `{ "checkbox": "W8" }` | フォームコントロール（リンクセル・ctrlProps・VML の 3 か所を揃える） |
| `{ "anchor": "１建築基準法(以下", "mark": "circle" }` | 書き出した PDF のその文字に ○ / レ点を描く |

```jsonc
// 安全証明書の「建築物の区分」。選択肢ごとに PDF 上の印の位置を持つ。
{ "key": "building_category", "label": "建築物の区分", "type": "select", "required": true,
  "options": [
    { "value": "1", "label": "法第20条第1項第1号に…",
      "target": { "anchor": "１建築基準法(以下", "mark": "circle" } }, … ] }

// 必要壁量の「0. 設計の用途」。選択肢ごとに配布物のチェックボックスを持つ。
{ "key": "usage", "label": "0. 設計の用途", "type": "select", "required": true,
  "options": [
    { "value": "performance", "label": "住宅性能表示制度を利用",
      "target": { "checkbox": "W8" } }, … ] }
```

**この 2 つが同じ形になることが、語彙が本物である一番強い証拠です。**
別々のツールで別々に書かれた「○ を付ける」と「チェックを入れる」が、
**選択肢ごとの書き込み先**という 1 つの概念に収まりました。節の `toggle` も
同じで、`{ "checkbox": "W52" }` を持つ `checkbox` 型の欄が節を開閉している、
というだけになります。

### 3.6 選択肢

| 書き方 | 例 |
| --- | --- |
| 直書き | `"options": ["←", "→", "傾斜無"]` |
| 表の参照 | `"options_ref": "qualification"`（レシピの `option_tables` を引く） |
| 連動 | `"cascade": { "role": "species", "of": "c2_1f_①_jas" }`（他の欄の値で表が決まる） |

### 3.7 雛形の在り処

```jsonc
// 同梱（必要壁量）
{ "from": "bundled",
  "path": "templates/worksheet.xlsx",
  "source": "templates/source.json",          // 版・取得元・sha256
  "version_cell": { "surface": "one_story", "ref": "V3" } }

// Drive（現況検査レポート・安全証明書）
{ "from": "drive", "kind": "xlsx" }           // kind: xlsx | google-doc
```

`from: "drive"` を書くと、エンジンが `GET /template` と `PUT /template` を
**生やします**。今 2 つのツールに同じ形で書かれている「Picker で選ばれた
fileId → ゴミ箱・種類・親フォルダの確認 → 共有設定へ『フォルダ + ファイル名』で
保存」は、この 1 行に畳まれます。

`kind` を自由な MIME 文字列にせず 2 つの名前にしてあるのは、**種類が違えば
読み方も記入のしかたも違う**ためです。3 つめの種類を増やすことは新しい機構を
増やすことなので、レシピではなくエンジンの変更になるのが正しい形です。

### 3.8 引き渡しと、ファイル名

```jsonc
{ "as": "download",                    // download | drive-pdf
  "path": "worksheets",                // POST /api/tools/<id>/worksheets
  "file_name": { "template": "必要壁量 表計算ツール（{surface.label}）_{property_name}",
                 "extension": ".xlsx",
                 "default":   "必要壁量 表計算ツール.xlsx" } }
```

`{…}` は入力欄の key と、面のラベル（`{surface.label}`）で埋めます。埋まらな
かった場合と、使えない文字を落とした結果が空になった場合は `default` を使い
ます。今 3 つのツールにばらばらにある `_sanitize` / `ensure_pdf_extension` /
`default_file_name` の 3 つは、この 1 つの規則になります。

`as: "drive-pdf"` は「保存 / 別名で保存」（土台の `resolve_pdf_destination`
/ `save_pdf`）で、`POST /certificates` の応答（`mode` / `fileId` /
`fileName` / `webViewLink` / `warnings`）もエンジンが組み立てます。

### 3.9 読み戻しと、突き合わせ

```jsonc
"read_back": {
  "metadata_key": "/PortalStructuralCert",     // 自分が作った PDF は完全復元
  "rules": [ { "type": "line_regex", "pattern": "^委託者(?P<client_name>.*)殿$" },
             { "type": "right_of",   "label": "建築物の所在地", "field": "building_address" } ] }

"verify": { "op": "wallQuantity", "header": "X-Wall-Quantity-Verification" }
```

読み戻しは既に宣言的（`parse_rules`）なので、そのまま語彙に入ります。
印が付いているかの判定は、§3.5 の `anchor` を逆から読むだけです。

`verify` は雛形記入ではありませんが、**「画面が出した値とサーバが出した値を
突き合わせて、食い違いをヘッダで知らせる」という段取りは記入の流れの一部**
なのでエンジンが持ちます。計算そのもの（wasm）は今までどおり portal のもので、
レシピが渡すのは「どの op を呼ぶか」だけです。

## 5. 画面はどうするか

この語彙は API 専用のものではありません。`/config` が配るのは `form` そのもの
なので、**画面も同じ語彙からフォームを組み立てられます**。ただし今回は
画面を寄せません。理由は次のとおりです。

* 3 つの画面には、語彙に無い**そのツール固有の振る舞い**が実際にあります
  ——部屋の見出しを入力に追従させる、キーボード出現時の sticky ヘッダの補正、
  証明日を和暦に直して 3 つの欄へ割る、出力結果の表を wasm の結果から描く、
  釘配列図の縮尺。汎用のフォームレンダラを先に作ると、これらの逃げ道を
  想像で設計することになります
* 語彙が本当に 3 つを覆うかは、**API 側で 1 度通してみるまで確定しません**。
  画面まで同時に載せ替えると、語彙の間違いが 2 層に広がります

**順序として、まず API 側で語彙を確かめ、それから画面を載せ替えます**（§8）。
画面を寄せるときも、汎用のレンダラが描くのは「節・かたまり・入力欄」までで、
ツール固有の振る舞いは今と同じくツールの `main.js` が受け持つ形になります。

## 6. plugin-architecture.md との関係

**今のところ、何も差し替えません。** 統一は portal の中の作業なので、
[plugin-architecture.md](plugin-architecture.md) の §1〜§8（3 層の分け方・
3 つの継ぎ目・`tools.json` による版の固定・循環の避け方・ツール単体での
プレビュー・更新の流れ）はそのまま生きていますし、§9 の移行の順序も
まだ有効です。

**分割すると決めたときに**、§9 の第 3・4 段が次のように変わります。

| | plugin-architecture.md §9 | 分割する場合 |
| --- | --- | --- |
| リポジトリ | ツール 4 つ ＝ 4 リポジトリ | 雛形記入の 3 つ ＝ 1 リポジトリ ＋ 面材張り大壁 ＝ 1 リポジトリ |
| `tools.json` の行数 | 4 エントリ | 2 エントリ |
| ツールを増やす（雛形記入型） | 新しいリポジトリを 1 つ作る | portal にレシピを 1 枚足す |

**そのとき §1 の原則と緊張します。** plugin-architecture.md §1 は
「そのツールにしか出てこないものはツールのリポジトリに置く」としています。
レシピはまさに「そのツールにしか出てこないもの」ですが、この設計では
portal に残ります。意図的な例外にする理由は 2 つあります。

1. **レシピは論理ではなく記述です。** 読むのに前後の文脈が要らず、1 つの
   ツールを直すときに他のツールのレシピを読む必要はありません。分割の目的
   （ツールを直すときに読む範囲を狭める）は、**論理については達成されます**
2. **語彙とレシピの版はそろっている必要があります。** レシピを N 個の
   リポジトリへ散らすと、語彙に何か足すたびに N 回の追従 PR が要ります
   ——これは plugin-architecture.md §8 が「払うもの」として挙げたものそのもの
   です

**正直に言うと、分割したとしても利得の一部は得られません。** portal には
148 kB の mapping が記述として残り続けるためです。分割で出ていくのは
エンジン（3 モジュール 1,242 行を統一した結果なので、それより小さい）だけで、
**これが「今は分割しない」と判断したもう 1 つの理由**でもあります——
出ていく量が、往復の費用に見合いません。

## 7. 語彙に収まらなかったもの

無理に押し込まず、portal 側に残すものを明示しておきます。

* **配布物の番人**（`wall_quantity_mapping.json` の `guard`）… 配布物の
  数式・ラベル・出力欄を控えておき、改訂されたら気付くためのテスト資産です。
  雛形記入の流れではなく「この雛形が想定どおりか」の検査なので、ツールの
  テストとして portal に残します
* **画面側の警告**（傾斜が閾値を超えていないか等）… 出力は止めずに確認を
  促すもので、判定は画面にあります。`validation` の値はレシピに入りますが、
  判定そのものは画面のまま
* **和暦の組み立て**… 証明日を年号・月・日の 3 欄へ割るのは画面の仕事
* **面材張り大壁 計算ツール**… **雛形を持ちません**（計算書 PDF をゼロから
  組み立てる）。このユニットには入らず、plugin-architecture.md §9 のとおり
  単独のリポジトリとして切り出します

### 決めておくこと — xlsx への書き方を 1 つに寄せる

今、xlsx への書き込みは 2 通りあります。

| | 現況検査レポート | 必要壁量 |
| --- | --- | --- |
| 使うもの | openpyxl（ブックを読み直して書き出す） | `xlsx_fill.py`（zip の中の触る場所だけ書き換える） |
| 失うもの | チェックボックス・図・VML・印刷設定は復元されない | 何も失わない |
| 保護シート | ロックされたセルへは**黙って書かない** | 確認しない |

**一本化はしません。** 当初は「`xlsx_fill` に寄せ、保護シートの確認は
警告に変える」と書いていましたが、実装とテストを読み直して**取り下げました**。

保護シートの確認は事故ではなく、**意図された仕組み**でした。`mapping.json` の
覚え書きにこう書いてあります——

> 入力例ブロック（グレーアウトされた最初の部屋）のセルはロックされたまま
> 維持し、実際の記入ブロックのセルだけ `locked=False` に設定することで
> 書き込み可否を制御できる。

つまり雛形の作り手が、ロックによって「ここは書くな」を指示しています。しかも
これは `test_reports.py` の **4 本のテスト**が明示的に守っています
（ロックされたセルへ書かない・アンロックされたセルへは書く・1 部屋目が
黙って失われない・ロックされたセルは記入例を保ったまま残る）。

したがって 2 つの書き方は**どちらも要る**もので、選ぶのは雛形の性質です。

| 雛形の性質 | 使うもの |
| --- | --- |
| **配布物そのものを返す**（チェックボックス・図・VML・印刷設定を 1 つも失えない） | `xlsx_fill` |
| **書ける場所が雛形側で指示されている**（保護シートのロック） | openpyxl |

レシピはこれを性質として書き、エンジンが道具を選びます。

```jsonc
"fill": { "preserve": "everything" }        // 必要壁量
"fill": { "respect_sheet_protection": true } // 現況検査レポート
```

> **この訂正は、1 ツールずつ載せ替える進め方が働いた最初の例です。**
> 3 つまとめて書き直していたら、4 本のテストが落ちてから気付くことになり、
> しかも「テストのほうを直す」という誤った逃げ道が見えていたはずです。

## 8. 移行の順序

**ツールのルーターは互いに独立しているので、1 ツールずつ載せ替えられます。**
途中の段では、載せ替えた 1 つがエンジンの上に、残りが今までのモジュールの
ままで**共存します**。どの段でも止められ、どの段でも戻せます。

順序は**語彙が増える順**です。小さいものから始め、次のツールが来るたびに
語彙が育ちます。

| | 載せ替えるもの | そこで語彙に加わるもの |
| --- | --- | --- |
| **第 1 段** | **現況検査レポート**（`excel_report.py` 214 行） | かたまり（単発・繰り返し）・`cell` / `column`・Drive 雛形と設定 API・ダウンロード |
| 第 2 段 | **必要壁量**（`wall_quantity.py` 500 行） | 面・節の `toggle`・条件（`visible_when` / `required_when` / `fixed_when`）・選択肢の表と連動・`checkbox`・同梱雛形・`verify` |
| 第 3 段 | **構造計算安全証明書**（`structural_cert.py` 528 行） | `placeholder`・`anchor`（印）・`filled` 述語と前提の連鎖・Drive への保存・読み戻し |

各段で確かめるのは同じ 2 つです。

* **既存のテストが 1 つも落ちないこと。** 3 つのツールには合計 **181 本**の
  バックエンドテストがあり（9 ファイル）、これがそのまま合否の判定になります。
  内訳は現況検査レポート 33 本（うち雛形設定 API が 9 本）・必要壁量 65 本・
  安全証明書 65 本・配布ページの更新確認 18 本
* **URL と応答の形が変わらないこと**（§4 に挙げた `GET /settings` の 1 か所を除く）

> **第 1 段を終えたら、一度立ち止まります。** 語彙が現実に耐えるかどうかは、
> 1 つ載せ替えてみればかなり分かります。おかしければ 1 PR の損で直せます。
> **3 つまとめてやると、間違いに気付くのが 3 倍遅れます。**

そのあとに続きうるもの（どれも独立に判断できます）。

| | やること |
| --- | --- |
| 画面 | 語彙の上へ載せ替える。汎用のレンダラは「節・かたまり・入力欄」まで、固有の振る舞いはツールの `main.js` に残す（§5） |
| 分割の練習 | 純粋ライブラリ（`xlsx_fill` / `pdf_tools` / `pdf_write`）でタグ → 版の固定 → 取り込みの往復を一度通す |
| エンジンの分割 | 語彙が動かなくなってから判断する。`portal-tool-template-fulfiller` へ移す |

## 9. トレードオフ（正直なところ）

**得られるもの**

* 同じ流れの 3 本の実装が 1 本になる。正規化・条件の評価・必須の確認・
  ファイル名の組み立て・雛形の設定 API が、それぞれ 1 つになる
* 雛形記入型のツールを増やすのが、**レシピ 1 枚**になる
* 「○ を付ける」と「チェックを入れる」のように、別々に書かれていたものが
  同じ概念に収まる。次のツールでも同じ道具が使える
* 直す範囲が読める。段取りの不具合は `template_fulfiller/`、記述の間違いは
  1 枚の JSON
* **分割するかどうかを、後から落ち着いて決められる。** 統一の結果が
  1 つのディレクトリにまとまるので、切り離すのは移動だけになる

**払うもの**

* **これはフレームワークです。** いちばん危ういのはリポジトリの境界ではなく、
  語彙の解釈器を新しく作ること自体です。→ 語彙は「今ある 3 つに実際に
  あるもの」だけで作り、**将来を想像して足さない**。§3 の語彙が実データの
  検査から出ているのはこのためです
* **エンジンが 3 つのツールに縛られます。** 4 つめの雛形記入型ツールが
  語彙に収まらない形だったとき、エンジンに手を入れることになります
* **1 つの段取りの不具合が 3 つのツールに出ます。** 今は 1 ツールで済んで
  いたものが 3 つに広がります。→ エンジンのテストは、3 つのレシピすべてを
  通す形で書きます
* **記述は減りません。** 148 kB の mapping はレシピになるだけで、量は
  そのままです。減るのは論理のほうだけです

**この設計を採らない選択肢との比較。** plugin-architecture.md §9 のまま
3 リポジトリに分けると、同じ流れの実装が 3 本のまま別々のリポジトリへ
散ります。片方を直したときにもう 2 つへ同じ修正を写す作業が、
**リポジトリを跨ぐぶん今より重くなります**。3 つが「雛形を編集して生成物を
得る」で本当に同じである以上、分ける線は**ツールごと**ではなく
**流れと記述の間**に引くほうが自然だと判断しました。**そしてその線は、
リポジトリを分けなくても引けます**——それが今回やることです。
