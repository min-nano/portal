# 雛形と設定をリポジトリの外で管理する（設定バンドル）

**このリポジトリは公開です。** 一方で、見積書・契約書等の作成ツールが扱う
**書類のフォーマットと見積り（報酬算定）のロジックは、事務所の外に出したくないもの**です。
本書は、**それらを 1 つもリポジトリに置かずに動かすための、土台側の仕組み**を決めます。

対象は土台（`portal_sdk`）で、特定のツールの設計ではありません。
これに載る最初のツールの設計は [contract-formatter.md](contract-formatter.md) にあります。

> **まだ実装していません。** 実装の順序は §12 にあります。

---

## 1. 何を隠すのか — 先に線を引く

「隠す」を曖昧にしたまま作ると、**隠せていないものを隠したつもりになる**のがいちばん危険です。
最初に、**公開されたままになるもの**を確定させます。

| | 見える | 見えない |
| --- | --- | --- |
| **リポジトリ**（公開） | 仕組み、スキーマ（キーの語彙と型）、式の評価器、画面の見た目、ダミーの値 | — |
| **Drive の設定フォルダ** | 事務所の Workspace 内で共有された人だけ | それ以外の全員 |
| **Firestore の発行済み版** | バックエンドだけ（クライアント SDK は全面拒否） | それ以外の全員 |

**リポジトリから読み取れないもの**（＝隠したいもの）:

- 書類に載る項目の**名前・並び・文言・必須条件**
- 雛形の**プレースホルダー名**と、条項そのもの
- 見積りの**表の値・単価・係数・丸め・積算の手順**
- どんな**書類の種別**を持っているか

**リポジトリから読み取れるもの**（＝隠せないもの）:

- **器の形**。「項目には key と label と必須条件がある」「計算は表引きと補間と丸めでできている」
  といった**語彙**は、スキーマと評価器としてリポジトリに残ります
- 画面のレイアウトと操作の流れ

> **器の形まで隠すことはできません。** 器を隠すには評価器ごと外に出すことになり、
> それは「コードを Drive に置いて実行する」ことです。**公開リポジトリに置いた評価器が、
> 非公開のデータを読んで動く**——ここが本書の設計の全体です。

> **告示の別表そのものは公開情報です**（官報・国交省のサイト）。隠すことで守られるのは
> 別表の数値ではなく、**事務所の単価・補正・値引きの根拠と、案件をどう類型に当てはめるか**
> という組み立てのほうです。とはいえ**両者は同じ計算の中で混ざる**ので、
> 分けて置くと「どちらに書いてあるか」を毎回考えることになります。
> **本書は計算をまるごと外に出します。** リポジトリ側には数値を 1 つも残しません。

## 2. 置き場所 — 3 つに分ける

```
  Drive（原本。人が編集する）            Firestore（発行済み。実行時に読む）        リポジトリ（公開）
  ────────────────────────────         ──────────────────────────────────       ──────────────────
  設定フォルダ/                          tool_resources/<ツール>                   スキーマ
    bundle.json         ──[発行]──→       published_hash ─┐                       評価器（core/）
    fee-rules.json                        revisions/<hash>┘ ←── 実行時はここだけ    画面
    契約書.gdoc      ─────────────────────────────────────────→ 生成時に本人の代理で複製
    重要事項説明書.gdoc
```

| 置き場所 | 何を | なぜそこか |
| --- | --- | --- |
| **Drive の設定フォルダ** | 雛形（Google ドキュメント / xlsx）と、定義の JSON | 人が編集し、版履歴が残り、共有設定で権限が決まる。**すでに雛形でそうしている**（`excel-report-formatter`） |
| **Firestore** | **発行済みの版**（JSON の中身そのもの）と、どの版を使うかの目印 | 実行時に人の編集が直接効かない。Drive を叩かないので速く、Drive が落ちても書類が作れる |
| **リポジトリ** | スキーマ・評価器・画面・**ダミーのバンドル** | 中身を持たない。持たないので公開できる |

**Drive と Firestore の役割が違うことが、この設計の要点です。**
Drive は**編集する場所**、Firestore は**実行する版**。あいだに「発行」という人の操作が入ります（§3）。

> **雛形（Google ドキュメント）だけは Drive に残ります。** Docs API の置換は Drive 上の
> ファイルに対して行うもので、中身を持ち出しても意味がないためです。したがって
> **雛形の取得は今までどおり実行ユーザー本人の代理で行われ、本人に閲覧権限が無ければ失敗します。**

## 3. 発行（publish）— Drive の編集を、そのまま本番にしない

```
[設定] → Drive のフォルダを選ぶ（Picker）
       → [読み込んで検証]  … Drive から読み、検証し、前の版との差分を出す（まだ本番は変わらない）
       → 検証の結果を見る  … 項目数・表の要素数・自己テストの結果・雛形の照合
       → [発行]            … Firestore へ格納し、目印を新しいハッシュへ向ける
```

| 決めごと | なぜ |
| --- | --- |
| **実行時は Firestore の発行済み版だけを読む。Drive を見ない** | Drive での編集途中・保存ミス・誤削除が本番へ即座に出ない。**「設定を直したら書類が作れなくなった」を構造的に起こさない** |
| **発行の単位はフォルダ全体で、版はハッシュ 1 つ** | 「書式は新しい版、単価は古い版」という組み合わせを作らない。**再現するときに指すものが 1 つで済む** |
| **発行できるのは、その設定フォルダに Drive の編集権限を持つ人だけ** | 権限を portal 側に作らない。**境界は Drive の共有設定**という portal の作法（README「セキュリティ / 権限モデル」）のまま |
| **前の版へ戻せる** | 発行済みの版は消さずに残す（`revisions/<hash>`）。戻すのは目印を旧ハッシュへ向けるだけ |
| **検証に落ちた内容は発行できない** | 壊れた設定が本番に出る経路を無くす。落ちた理由は**どのファイルの、どのキーか**まで出す |

### 発行時に検証すること

**ここが、公開 CI で守れなくなったものを引き受ける場所です**（§7）。

| # | 検証 | 落ちたときの意味 |
| --- | --- | --- |
| 1 | **スキーマ**（必須キー・型・重複キー・未知のキー） | 書き間違い |
| 2 | **参照の解決**（項目が指す雛形・プレースホルダー・表・設定値が存在するか） | 消し忘れ・打ち間違い |
| 3 | **式の静的検査**（未知の識別子と関数、循環参照、ノード数と深さの上限、定数 0 での除算、出力が丸めを通っていること） | 計算が実行時に壊れる形になっている |
| 4 | **表の形**（軸が単調増加・欠測なし・行の長さが揃っている） | 転記の抜け |
| 5 | **自己テスト**（バンドルが持つ期待値を評価器で流す。§7） | **値の転記ミス** |
| 6 | **雛形の照合**（Docs API で本文を読み、必須項目のプレースホルダーが実在するか） | 雛形と定義がずれている |
| 7 | **大きさ**（Firestore の 1 ドキュメント上限 1 MiB に収まるか） | 分割が要る（§4） |

**6 が効きます。** 従来は「生成しようとして初めて雛形のずれに気付く」でしたが、
**発行の時点で分かります。** 雛形は発行後も編集できてしまうので、生成時の
`occurrencesChanged` による検証（[contract-formatter.md](contract-formatter.md) §4.3）は残します。

## 4. 実行時 — 何を、どう読むか

```
要求 → 目印（tool_resources/<ツール>）を読む → published_hash
     → revisions/<hash> を読む → gzip を解いて JSON → 評価器へ
```

| 決めごと | なぜ |
| --- | --- |
| **版（`revisions/<hash>`）はプロセス内で無期限にキャッシュする** | ハッシュで名前が付いているので**中身が変わらない**。変われば別の名前になる |
| **目印は短い期間だけキャッシュする（60 秒）** | 発行してから全インスタンスに行き渡るまでの時間を、この一言で説明できるようにする |
| **JSON は正規化して gzip で格納する**（Firestore の bytes 型。base64 にしない） | 数値の並ぶ JSON はよく縮む。正規化（キーの並び順・空白）を決めるのは、**同じ内容が常に同じハッシュになる**ようにするため |
| **1 MiB を超えるときは発行時に分割する**（`revisions/<hash>/parts/<n>`） | 実行時は連結するだけ。**上限に当たったことが発行の時点で分かる**ようにする |
| **未発行なら 409** | 「設定が発行されていません。管理者が『設定』から発行してください。」既存の雛形未設定と同じ扱い |
| **スキーマの major が合わなければ 409** | バックエンドを更新したのに古い版が残っている、を黙って動かさない。文面で「発行し直してください」と出す |

**画面にもバンドルが要ります。** フォームを組み立て、入力のたびに金額を出すのは画面側だからです。
`GET /api/tools/<id>/config` が発行済みバンドルから導出して配ります（既存の `form_config()` の作法）。

> **バンドルはビルドに焼き込みません。** フロントエンドの静的ファイルは Firebase Hosting が
> **誰にでも配ります。** 認証の要る API から配ることが、隠す条件そのものです。
> ここは「画面に埋め込んだほうが速い」と考えたくなる場所なので、**理由をここに書いておきます。**

## 5. バンドルの形

**フォルダの中の JSON 群を、発行時に 1 つに束ねます。** ファイルを分けるのは、
**直す人と直す頻度が違う**からです（書式は法令改正のとき、単価は年に 1 度）。

```
設定フォルダ/
  bundle.json        # 束ねる宣言（スキーマ版・書類の種別・雛形の対応・部品の一覧）
  documents.json     # 書類ごとの項目・並び・必須条件・プレースホルダー
  fee-rules.json     # 見積りの表・係数・手順・印字・自己テスト
  契約書.gdoc / 重要事項説明書.gdoc / …   # 雛形（中身は Drive に残る）
```

**リポジトリに置くのはスキーマだけです。** 以下は**形を説明するための例**で、
値はすべて架空です（実在の様式・単価ではありません）。

```jsonc
// documents.json — 書式（何を、どの書類に、どの条件で載せるか）
{
  "schema": "portal.resource-bundle/1",
  "documents": [
    { "id": "doc_a", "label": "…", "template": "契約書", "file_name": "{date}_{name}.pdf" }
  ],
  "fields": [
    {
      "key": "field_a",
      "label": "…",              // 画面の見出しもエラー文もここから出る（コードに文言を持たない）
      "note": "…",               // 根拠・補足。画面のチェック表にそのまま出す
      "type": "text",
      "documents": ["doc_a"],    // どの書類に載るか。必須検証はこの集合に対してのみ行う
      "required_when": "true",   // 式（§6）。定数 true でも式として書く
      "placeholders": ["{{…}}"]
    }
  ],
  "sections": [ { "label": "…", "fields": ["field_a"] } ]
}
```

```jsonc
// fee-rules.json — 見積り（表・手順・印字）
{
  "schema": "portal.resource-bundle/1",
  "tables": {
    "table_a": { "axis": "in.area", "points": [100, 200], "rows": { "row_a": [10, 20] } }
  },
  "settings": ["unit_price", "tax_rate"],        // Firestore の事務所設定から読むキー
  "steps": [
    { "id": "hours",  "label": "…", "expr": "interp(table_a.row_a, in.area)" },
    { "id": "labor",  "label": "…", "expr": "step.hours * set.unit_price" },
    { "id": "total",  "label": "…", "expr": "round(step.labor * (1 + set.tax_rate), 1, 'floor')" }
  ],
  "output": "step.total",
  "print": [ { "step": "labor", "label": "…", "when": "step.labor > 0" } ],
  "selftests": [ { "in": { "area": 150 }, "set": { "unit_price": 1000 }, "expect": { "total": 16500000 } } ]
}
```

**印字する文言も、書類の種別も、バンドルにあります。**
リポジトリのコードには「契約書」も「業務報酬内訳書」も出てきません。
**書類を 1 つ増やすのは、雛形と定義を足して発行するだけ**で、コードは変わりません。

## 6. 計算をデータで書く — 式と評価器

**評価器は `core/`（Rust → wasm）に置きます。** 画面とサーバーが同じ実装を動かす、という
既存の作法（必要壁量・面材張り大壁）をそのまま使えます。**違うのは、計算の中身が
`.wasm` ではなくバンドルから来ることだけ**です。

```
core/src/calc/
  expr.rs     # 式の構文解析と評価（純粋。I/O なし）
  table.rs    # 表引きと補間
  money.rs    # 有理数と丸め
  check.rs    # 発行時の静的検査（§3）
```

### 式に書けるもの

| | |
| --- | --- |
| 参照 | `in.<キー>`（入力）・`set.<キー>`（事務所の設定値）・`step.<id>`（前の手順の値）・`<表名>.<行名>` |
| 演算子 | `+ - * /` `< <= > >= == !=` `&& \|\| !` |
| 関数 | `if` `min` `max` `abs` `sum` `product` `coalesce` `lookup` `interp` `round` |
| 上限 | ノード 512・深さ 32・手順 200・表の要素 20,000 |

**書けないもの**: 代入、ループ、再帰、関数定義、文字列の演算、外部参照。
**式は純関数で、同じ入力からは必ず同じ値が出ます。**

| 決めごと | なぜ |
| --- | --- |
| **数は有理数（分子・分母とも整数）で持つ** | 補間も税率も除算で分数になる。浮動小数点を使わないという既存の方針（`core/src/format.rs`）を、外から来る式でも守る |
| **丸めは `round` を書いた手順でだけ起きる** | どこで端数が消えたかが定義に書いてある状態にする。**出力が `round` を通っていることは発行時に検査する** |
| **失敗は 409（バンドルの不備）で、500 にしない** | 壊れているのはコードではなく設定。**どの手順で落ちたか**を文面に出す |
| **評価器の側に既定値を持たない** | 「設定が無ければ 1.0」のような親切を入れると、**リポジトリに数値が 1 つ生まれる**。未定義は未定義として発行時に落とす |

> **公開された評価器が非公開のデータを読む、という形の安全性**は、
> 「式に I/O が無い」「ループが無い」「上限がある」「静的検査を通ったものしか発行できない」
> の 4 つで担保します。バンドルを書けるのは事務所の管理者だけですが、
> **壊れた式で落ちないことは評価器の責任**です。

## 7. 公開 CI で守れなくなるもの — 自己テストで引き受ける

**リポジトリに値が無くなると、CI では「値が正しいこと」を確かめられません。**
これは失うものです。黙って失わずに、置き換えます。

| | 以前（値がリポジトリにある） | 本設計 |
| --- | --- | --- |
| 表の転記ミス | CI で原本と突き合わせる | **バンドルが持つ自己テストを、発行時に評価器で流す。1 件でも合わなければ発行できない** |
| 式の間違い | CI のテスト | 同上 ＋ 発行時の静的検査（§3 の 3） |
| **評価器の正しさ** | — | **公開 CI で守る。** ダミーのバンドル（`backend/tests/fixtures/bundle-sample/`）で、補間・丸め・条件・上限・エラーを固定する |

**自己テストは「その値を使ったときに、いくらになるか」を事務所が書きます。**
原本（告示・社内規程）と突き合わせるのは人の作業で、**その結果が自己テストとして残ります。**
発行の要約に「自己テスト 42 件 合格」と出し、**誰がいつ発行したか**とともに記録します。

> **CI が本番の値を持たないことは要件です。** テストは「エンジンが仕様どおりに動くこと」
> だけを主張し、事務所の値は 1 つも登場しません。**ダミーは架空の様式・架空の単価**で書き、
> 実在の氏名・住所・金額を使いません。

## 8. 版の記録と再現性

**生成した PDF に、使ったバンドルのハッシュを埋めます。**

```json
{ "bundle": { "hash": "3f2a1c9e4b70", "publishedAt": "2027-02-01T…" }, "…": "…" }
```

- PDF を開き直したとき、**現在の発行版と違えば画面に出す**（「この書類は別の版の設定で作られています」）
- **再計算はしません。** 金額は PDF に入っている値が正です。設定を後から変えても過去の書類は変わりません
  （[contract-formatter.md](contract-formatter.md) §7 の「マスタを参照しない」と同じ理由）
- 監査で「この見積りはどの規則で出たのか」と問われたら、**ハッシュから `revisions/<hash>` を引けます**

## 9. 隠しきれないこと（限界）

**正直に書いておきます。** 隠したつもりで隠せていない、が最も危険だからです。

| 限界 | 実際の影響 | どうするか |
| --- | --- | --- |
| **バンドルは画面へ配られる**（フォームの組み立てと金額の即時表示に要る） | **サインインできる社内ユーザーは、開発者ツールで中身を読める** | 受け入れる。読める相手は事務所の人間で、書類を作る当人。**外部に対しては隠れている** |
| Firestore の発行済み版には、雛形フォルダの閲覧権限が効かない | 雛形（条項本文）は読めないが、**定義と単価表は社内の全員が読める** | 絞りたい場合の設定 `require_template_access` を置く（`/config` を返す前に、雛形フォルダの閲覧可否を本人の代理で確かめる。Drive のメタデータ取得 1 回） |
| スキーマと評価器は公開のまま | 「どういう形の計算をしているか」は分かる | 受け入れる（§1） |
| リポジトリの履歴 | 一度公開したものは消えない | **最初から値を入れない。** 既存ツールの mapping を後から移すときは、履歴に残ることを承知の上で判断する（§11） |

## 10. 土台に足すもの

**ツールごとに書きません。** 土台に 1 つ置き、使うツールがそれを借ります
（[shared-logic.md](shared-logic.md) の作法。土台とツールのあいだに新しい層は作りません）。

```
backend/app/
  resource_store.py     # 発行済み版の読み書き（Firestore）。settings_store.py と同じ位置づけ
  resource_bundle.py    # 束ね・正規化・ハッシュ・スキーマ検証・参照解決
  portal_sdk.py         # get_bundle(tool_id) / publish_bundle(...) を足す
  google_drive.py       # フォルダ内のファイル一覧、capabilities（編集権限の確認）を足す
core/src/calc/          # 式の評価器（§6）
frontend/src/components/
  portal-resource-bar   # 「設定フォルダを選ぶ → 検証 → 発行 → 版を戻す」の画面部品
```

| メソッド | パス | 用途 |
| --- | --- | --- |
| GET | `/api/tools/<id>/resources` | 発行状態（ハッシュ・日時・発行者・雛形の一覧・自己テストの結果） |
| POST | `/api/tools/<id>/resources/validate` | Drive の現在の内容を読んで**検証だけ**する（差分を返す。本番は変わらない） |
| POST | `/api/tools/<id>/resources/publish` | 検証して発行する（**Drive の編集権限が要る**） |
| POST | `/api/tools/<id>/resources/rollback` | 目印を過去のハッシュへ戻す |
| GET | `/api/tools/<id>/config` | 発行済みバンドルから導出したフォーム定義（既存の作法のまま） |

Firestore 上の位置（チャンネルの下。既存の `tool_settings` と並びます）:

```
static-channels/production/tool_resources/<ツール>                 ← 目印
static-channels/production/tool_resources/<ツール>/revisions/<hash> ← 中身（不変）
```

## 11. 環境ごとの扱い

| 環境 | バンドル |
| --- | --- |
| 本番（`static-channels/production`） | 事務所が発行した版 |
| 開発（`static-channels/development`） | **ダミーを発行して使う。** 本番の値をローカルへ持ってこない |
| PR プレビュー（`preview-channels/pr-<番号>`） | 空。画面は「未発行」の表示になる。必要ならダミーを発行する |
| CI | Firestore を使わない。ダミーのバンドルをフェイク経由で流す |

**「本番の設定が無くても、CI もローカルも通る」ことが要件です。**
既定のチャンネルが development であること（`config.settings_channel_path()`）が
そのまま効き、**設定ミスの症状は必ず「未発行に見える」になります。**

## 12. 既存のツールをどうするか

**移しません。今のところ、移す理由があるのは新しいツールだけです。**

| ツール | 今どこに | どうするか |
| --- | --- | --- |
| `excel-report-formatter` | 雛形は **Drive**（社外秘フォーマット）、定義は `mapping.json` | **雛形はすでに外。** 定義を移すかは、実際に困ったときに決める |
| `structural-cert-formatter` | 雛形は Drive、定義は `structural_cert_mapping.json` | **移さない。** 第四号書式は省令の様式で、公開されている |
| `wall-quantity-calculator` | 表計算ツールを**同梱**（`backend/app/templates/`） | **移さない。** 誰でも配布ページから同じものを入手できる |
| `timber-panel-shear-calculator` | 計算は `core/`。グレー本の式 | **移さない。** 公刊物の計算法 |
| **見積書・契約書等の作成ツール** | （未実装） | **最初からバンドルで作る**（[contract-formatter.md](contract-formatter.md)） |

> **先回りして一般化しません**（shared-logic §5）。土台に置くのは、
> **実際にそれを必要とするツールが 1 つ現れたとき**です。
> 既存の 4 つは今のままで困っていません。

## 13. 実装の順序

**どの段も単独で完結し、途中で止めても中途半端な状態は残りません。**

| | やること | 合否 |
| --- | --- | --- |
| **第 1 段** | **束ねと検証**（`resource_bundle.py` ＋ スキーマ ＋ ダミーのバンドル） | ダミーが検証を通り、壊したダミーが**理由つきで**落ちる |
| 第 2 段 | **発行と読み込み**（`resource_store.py` ＋ Firestore ＋ キャッシュ ＋ ロールバック） | 発行 → 読み込み → 戻す、が往復する。フェイクの Firestore で回る |
| 第 3 段 | **式の評価器**（`core/src/calc/`。静的検査と自己テストを含む） | 補間・丸め・条件・上限・エラーが固定される。**画面とサーバーが同じ値を出す** |
| 第 4 段 | **発行の画面**（`portal-resource-bar`。検証結果と差分の表示） | 検証に落ちたバンドルを発行できないこと |
| 第 5 段 | **雛形の照合**（発行時に Docs 本文とプレースホルダーを突き合わせる） | プレースホルダーの無い雛形で発行が落ちること |

第 1・2 段はツールが無くても書けます（ダミーのバンドルだけで完結します）。
第 3 段は[contract-formatter.md](contract-formatter.md) の Phase 2（見積り）に、
第 5 段は同 Phase 1（書類の生成）に噛み合います。

## 14. 決めごとの一覧

| # | 決めごと | なぜ | 節 |
| --- | --- | --- | --- |
| 1 | 実行時は Firestore の発行済み版だけを読み、Drive を見ない | 編集途中が本番へ出ない。速い。Drive の障害で止まらない | §3 |
| 2 | 発行の単位はフォルダ全体、版はハッシュ 1 つ | 再現するときに指すものが 1 つで済む | §3 |
| 3 | 発行できるのは Drive の編集権限を持つ人 | 権限の仕組みを portal に作らない | §3 |
| 4 | 検証に落ちた内容は発行できない | 壊れた設定が本番に出る経路を無くす | §3 |
| 5 | 計算はデータで書き、評価器だけをリポジトリに置く | 数値を 1 つもリポジトリに残さない | §6 |
| 6 | 数は有理数で持ち、丸めは `round` の手順でだけ起きる | 端数の消える位置が定義に書いてある状態にする | §6 |
| 7 | 評価器に既定値を持たない | 親切な既定値は、リポジトリに生まれる数値そのもの | §6 |
| 8 | バンドルは自己テストを持ち、発行時に流す | 公開 CI で守れなくなった「値の正しさ」を引き受ける | §7 |
| 9 | 生成物にバンドルのハッシュを埋め、再計算しない | 過去の書類の再現性 | §8 |
| 10 | バンドルはビルドに焼き込まず、認証の要る API から配る | 静的ファイルは誰にでも配られる | §4 |
| 11 | 既存ツールの定義は移さない | 公開されている様式・公刊物の計算法を隠しても得るものがない | §12 |
