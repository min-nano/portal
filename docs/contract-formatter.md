# 見積書・契約書等 作成ツール（`contract-formatter`）— 設計

設計等業務委託契約書・重要事項説明書・変更契約書・業務報酬内訳書を、1 つの入力から作ります。

**このツールはまだ実装していません。** 本書は、[min-nano/contract](https://github.com/min-nano/contract)
で検討した「建築士事務所の契約書類 作成支援」を、**portal のツールとしてどう作るか**に
落としたものです。実装に入る前に読む文書であり、着手の順序は §11 のロードマップにあります。

> **見積書だけは先に実装しました**（`quotation-formatter`。README「見積書 作成ツール」）。
> 重ねの仕組みを待たずに作れると分かったためです。分担は §6.8 に書いてあります。

> **このリポジトリは公開です。二層に分けます。**
> **告示・法令に書いてあること**（別表・難易度係数・法定記載事項）は**リポジトリに置きます**——
> 官報と e-Gov で誰でも読めるものを隠しても得るものがなく、**リポジトリに置くほうが
> 原文との突き合わせを CI で守れる**からです。
> **非公開にするのは、事務所が独自に決めた係数・積算のロジック・書類の書式と文言**で、
> これらは **Drive で管理し、検証して「発行」したものを土台に重ねます**
> （仕組みは [external-resources.md](external-resources.md)）。
> **本書に出てくる事務所固有の例はすべて架空です。**

## なぜ portal に置くのか

改正建築士法（令和8年法律第74号、2026-07-31 公布）で、**建築士が行う設計・工事監理の委託を
受けるすべての契約が書面の相互交付の対象**になりました（法22条の3の3第1項）。
延べ面積300㎡超という面積要件が撤廃されたため、**住宅を含む全案件**で法定記載事項を
満たした契約書面と重要事項説明書を作ることになります。施行は公布から1年以内、
すなわち**遅くとも2027年7月31日**です。

必要なのは「法定記載事項を漏らさない書類を作ること」と「報酬を算定すること」だけで、
交付・承諾・受領・保管は人の操作で完結します。そこまで絞ると、**必要なものは
構造計算安全証明書 作成ツールとほぼ同じ形**になりました。

| 必要なもの | portal にあるか |
| --- | --- |
| 社内ユーザーの認証 | **ある**（Clerk。Google ログイン + 許可ドメイン） |
| Google ドキュメントの雛形を複製して置換し、PDF へ書き出す | **ある**（`google_docs.replace_all_text` / `google_drive.export_file`） |
| 雛形とファイルを Drive から選ぶ | **ある**（Google Picker。代理アクセストークンで発行） |
| PDF を Drive へ保存（上書き / 別名で保存）し、版履歴を残す | **ある**（`<portal-edit-bar>` / `<portal-save-bar>` / `<portal-save-dialogs>`） |
| PDF に入力を埋め込み、開き直して復元する | **ある**（`structural_cert.finalize_pdf` / `parse_pdf`） |
| 雛形が改訂されて置換が起きなかったことの検知 | **ある**（`missing_placeholder_warnings`） |
| フォーム定義を単一の情報源から配信する | **ある**（`form_config()`） |
| 画面とサーバーで同じ計算を動かす | **ある**（`core/` の Rust → wasm） |
| 入力漏れのある節を自動で開く折り畳みセクション | **ある**（`<portal-section>`） |
| CI / PR プレビュー / デプロイ | **ある** |
| **事務所オリジナルの係数・ロジック・書式を、リポジトリの外から差し込む** | **無い。土台に足す**（[external-resources.md](external-resources.md)） |

**新しく書くのは「式の評価器」と「重ねを差し込む仕組み」、そして告示のルールだけです。**
**事務所が独自に決めたものは、コードではなくデータとして事務所が持ちます**（§4・§6.5）。
独立したシステムにすると、
Clerk・domain-wide delegation・Picker の APIキー・Cloud Run・CI・デザインシステムを
もう一組**運用し続ける**ことになり、得られるものは「リポジトリが分かれていること」だけでした。
このツールを使うのは事務所の人間だけで、それは portal の他のツールと同じ性質です。

### contract リポジトリとの分担

**contract は実装を持たないドキュメントのリポジトリとして残ります。**

| どこに置くか | 何を |
| --- | --- |
| **contract** | 法令要件（条文ベース）、条文とキーの対応、報酬算定の仕様、業務フロー・運用手順・規程・メール定型文、ADR |
| **portal**（本書） | **portal の土台にどう載せるか**、重ねとフォームの**形**、API、評価器の構成、テスト、ロードマップ |
| **`core/rules/`（リポジトリ）** | **告示の別表・難易度係数・費目の構成・略算方法の単一の情報源**（公開。CI で原文と突き合わせる） |
| **`backend/app/contract_base.json`（リポジトリ）** | **法定記載事項のキー・必須条件・根拠条文の単一の情報源**（公開） |
| **Drive の設定フォルダ**（発行して使う） | **事務所固有の項目・並び・文言・雛形のプレースホルダー・独自の係数と手順の単一の情報源**（非公開） |
| **Firestore** | 事務所の情報と設定値（＝フォームの初期値と、式が読む `set.*`）、**発行済みの重ね** |

条文の調査と改正の追跡は portal の関心事ではありません。逆に、フォームの並びや文言を
contract 側に写すと二重管理になります。**contract が持つのは「どのキーがどの条文に対応するか」
だけ**で、それ以外は**土台と重ねが正**です。

> **単一の情報源が 2 つに分かれます。** 法令・告示に書いてあることは**リポジトリ**、
> 事務所が決めたことは**重ね**。分ける線は「原文があるかどうか」で、
> **原文があるものは、原文と突き合わせるテストで守るべきもの**です（§9.1）。

## 1. 何を作り、何を作らないか

**法令が要求しているのは「書類を作ること」であって、システムを持つことではありません。**

| | 担い手 |
| --- | --- |
| 法定記載事項を漏らさない契約書・重要事項説明書・変更契約書の作成 | **ツール** |
| 報酬の算定と業務報酬内訳書の作成 | **ツール** |
| 電磁的方法による交付の承諾、書面の交付、相手方からの受領 | 運用（メールの定型文） |
| 重要事項の説明・免許証の提示 | 運用（記録は重説書面の欄に残す） |
| 保管（電子帳簿保存法） | 運用（Drive + 事務処理規程） |

**持たないもの**: データベース、オブジェクトストレージ、発注者向け画面、決済、電子署名、
契約のステータス、期限アラート。

とくに**「契約のステータス」を持ちません**。交付も承諾も受領もシステムの外に出た以上、
`DRAFT → QUOTE_SENT → … → EXECUTED` のような遷移を検知する手段がありません。
**知らない状態を持つと、必ず実態とずれます。** 承諾を得たかはメールボックスを、
どこまで進んだかはチェックリストを見ます。

## 2. 土台のどこに載るか

portal の他のツールと同じく、**画面・API・計算の 3 層**にまたがります。
ツールが自分を名乗り、土台がそれを読みます（README の「🧩 土台とツール」）。

```
frontend/src/contract-formatter/
  tool.js            # マニフェスト（id・名前・説明・ページ・入口）
  page.html          # 画面の中身
  overlay.html       # 保存ダイアログ（<div id="app"> の外）
  main.js            # 画面の入口
  form-dom.js        # /config から組み立てる DOM
  form-logic.js      # 純粋ロジック（義務の適用判定・ファイル名の組み立て・入力の正規化）
  tool.css           # 法定記載事項チェック表の形（このツールにしか出てこない）

backend/app/
  tools/contract_formatter.py   # /api/tools/contract-formatter/** のルーター
  contract.py                   # 書類の生成・PDF の解析・必須検証
  contract_base.json            # 法定記載事項のキー・必須条件・根拠条文（土台。公開）

core/rules/
  kokuji8.json                  # 令和6年告示第8号の別表・難易度係数・略算方法（土台。公開）
  kokuji670.json                # 平成27年告示第670号の別表・検査費・略算方法（土台。公開）
```

**事務所固有のものは、ここには現れません。** 独自の係数・手順・書式・文言は重ねにあり、
`contract.py` がするのは「合成されたルールのとおりに検証し、置換し、書き出す」ことだけです。

```
Drive の設定フォルダ（事務所が管理する。リポジトリの外・非公開）
  overlay.json / fee-overlay.json
  契約書.gdoc / 重要事項説明書.gdoc / 変更契約書.gdoc / 業務報酬内訳書.gdoc
```

**土台に足すものが 1 つあります**——重ねを差し込む仕組み
（[external-resources.md](external-resources.md)）。それ以外の部品はすべて既にあります。

| 使うもの | 何に | 今 |
| --- | --- | --- |
| `portal_sdk.get_rules` / `publish_overlay` | 発行済みの重ねを読む・発行する（土台との合成を含む） | **足す** |
| `core/src/calc/` の式の評価器と合成 | 報酬算定を、画面とサーバーの両方で同じに動かす | **足す** |
| `portal_sdk.tool_router` / `require_user` / `get_settings` | ルーターの取り付け・認証・共有設定 | ある |
| `portal_sdk.delegated_session` | 代理アクセス（実行ユーザー本人の権限で Drive / Docs） | ある |
| `portal_sdk.resolve_pdf_destination` / `save_pdf` | 保存先の解決と保存（上書き / 別名で保存） | ある |
| `google_docs.replace_all_text` | 雛形のプレースホルダー置換 | ある |
| `google_drive.export_file` | PDF への書き出し | ある |
| `pdf_tools` | 選択肢への印の描き込み・文字座標の取得 | ある |
| `nail_core` と同じ作法の wasm 呼び出し | 評価器をサーバー側でも動かす | ある |
| `<portal-section>` / `<portal-edit-bar>` / `<portal-save-bar>` / `<portal-save-dialogs>` | 節の開閉・ファイル操作 | ある |
| `src/core.js` | 画面から wasm を読む | ある |

### API

portal の既存のエンドポイントに揃えます（`/api/tools/<id>/...`）。

| メソッド | パス | 用途 |
| --- | --- | --- |
| GET | `/api/tools/contract-formatter/config` | フォーム定義（**土台と重ねを合成して導出**） |
| GET | `.../resources` | 発行状態（重ねのハッシュ・土台の版・日時・発行者・雛形の一覧） |
| POST | `.../resources/validate` `.../resources/publish` `.../resources/rollback` | Drive の内容の検証・発行・版戻し（土台が出す。→ [external-resources.md §10](external-resources.md)） |
| GET / PUT | `.../settings` | 事務所の情報と設定値（＝フォームの初期値と、式が読む `set.*`） |
| POST | `.../documents` | 書類の生成と Drive への保存 |
| POST | `.../documents/parse` `.../documents/parse-drive` | PDF の読み込み（再編集） |

**雛形ごとの `PUT /template` はありません。** 雛形は設定フォルダの中にあり、
どの書類がどの雛形を使うかは**重ねが決めます**。**雛形が 4 つあっても、
設定する操作は「フォルダを選んで発行する」の 1 つ**です
（[shared-logic.md](shared-logic.md) 2.1 が挙げていた「同じ段取りを 4 回書き写す」は起きません）。

評価器の `.wasm` は portal 共通の配り方（`src/core.js`）に乗せ、
このツール専用のエンドポイントは作りません。

## 3. 画面

**portal の他の PDF ツールと同じ考え方**（新規作成 / 開く / 保存 / 別名で保存）です。
利用者が「別のアプリを覚える」ことにならないようにします。

```
┌────────────────────────────────────────────────┐
│ 見積書・契約書等 作成ツール                  [設定]  │
├────────────────────────────────────────────────┤
│ 編集中: 20270415_山田太郎_3300000.pdf   [新規] [開く] │
├────────────────────────────────────────────────┤
│  ▼ 0. 契約の種類と相手方                              │
│      契約種別／建築士が行う業務か／相手方は建築主か       │
│      → ここで「何が必要か」が決まる（§5）              │
│  ▼ 1. 当事者                                        │
│  ▼ 2. 建築物の概要                                   │
│  ▼ 3. 業務の内容                                     │
│  ▼ 4. 従事する建築士・建築設備士・再委託                 │
│  ▼ 5. 報酬                        ┌──────────────┐ │
│      告示による算定／補正／支払の時期│ 法定記載事項     │ │
│  ▼ 6. 解除・特約                  │  法1項1号 ✓     │ │
│                                   │  法1項3号 ✓     │ │
│                                   │  規則7号 未入力  │ │
│                                   ├──────────────┤ │
│                                   │ 報酬（税込）     │ │
│                                   │  3,323,100 円   │ │
│                                   └──────────────┘ │
├────────────────────────────────────────────────┤
│ [契約書を作る] [重要事項説明書を作る] [業務報酬内訳書を作る] │
│ [メールの定型文をコピー ▾]                             │
└────────────────────────────────────────────────┘
```

| # | 決めごと | なぜ |
| --- | --- | --- |
| 1 | **法定記載事項チェック表を右に貼り付ける**（1080px 以上で 2 列。`.has-dock`） | 「何を漏らしていないか」が常に見えている状態が、このツールの価値そのもの |
| 2 | **報酬の額を入力のたびに出す** | 面積や業務範囲を動かしながら金額を見られる。必要壁量ツールと同じ作法 |
| 3 | **1 つの入力から契約書・重説書面・内訳書の 3 つを作る** | 同じ事項を 3 回入力させない。**必須検証だけは書類ごとに分ける**（§4.1） |
| 4 | **入力漏れのある節は自動で開く** | `<portal-section>` の既存の挙動 |
| 5 | **メールの定型文をコピーボタンで出す** | 案件の情報を差し込んだ状態で出す。手で書き起こさせない |
| 6 | **保存先は「編集中のファイル」か、そのつど選ぶフォルダ** | 共有設定として固定しない（証明書ツールと同じ） |
| 7 | **既定のファイル名は `YYYYMMDD_取引先名_金額.pdf`** | 電帳法の検索要件への備え（§7.2） |
| 8 | **[設定] は「フォルダを選ぶ → 検証 → 発行」の 1 つだけ** | 雛形は 4 つあるが、設定する操作は 1 つ。版がハッシュ 1 つで決まる（[external-resources.md §4](external-resources.md)） |
| 9 | **画面の見出しも文言も、配られた定義から出す** | 事務所固有の文言をコードに書かない。**書類を増やすのは発行するだけ**にする |
| 10 | **報酬の支払の時期は、回数・時期・金額の表で入れる** | 法1項4号の記載事項。**合計が報酬の額と一致しないときは警告を出す**（§6.9 の 11） |
| 11 | **略算方法が使えないと判定したら、実費積上げの入力に切り替える** | 「算定できません」で終わらせない。**区分ごとの人日で積む**（§6.9 の 14） |

## 4. 書類とフィールド — 法定記載事項は土台、書式は重ね

生成の流れは証明書ツールと同じです。**雛形そのものは書き換えません。**

```
フォーム入力
  → 雛形（Google ドキュメント）を複製
  → 複製に対して replaceAllText（{{報酬の額}} などのプレースホルダーを置換）
  → PDF へ書き出し
  → 複製を削除
  → 該当する選択肢に印を描き込む
  → フォーム入力そのものを PDF の文書情報へ埋め込む
  → Drive へ保存（上書き / 別名で保存）
```

条項の文言（解除・報酬・遅延損害金・紛争解決）は雛形に書いておき、**法務レビューの結果は
雛形の編集だけで反映できる**ようにします。雛形の**最終更新日時**を取得して契約書のフッターに
印字し（`雛形版: 2027-01-15 更新`）、どの版の条項で締結したかを書面から追えるようにします。

### 4.1 契約書と重説書面で必須項目セットが違う

**ここを共通化してはいけません。**

規則22条の2の2 は、重要事項説明書の省令事項を **「第十七条の三十八第一号から第六号までに
掲げる事項」** と定めています【原文確認済み】。**7号（実施の期間）・8号（種類、内容及び方法）は
含まれません。**

| キー | 記載事項 | 根拠 | 契約書 | 重説 | 必須になる条件 |
| --- | --- | --- | --- | --- | --- |
| `design_documents` | 作成する設計図書の種類 | 法22条の3の3第1項1号 | △ | △ | `scope` に**設計**を含むとき |
| `supervision_collation_method` | 工事と設計図書との照合の方法 | 同 1項2号 | △ | △ | `scope` に**工事監理**を含むとき |
| `supervision_report_method` | 工事監理の実施の状況に関する報告の方法 | 同 1項2号 | △ | △ | 同上 |
| `architects[]` | 従事する建築士の氏名・一級／二級／木造の別・構造設計一級／設備設計一級の別 | 同 1項3号 | ○ | ○ | 常に。**1 名以上** |
| `fee_amount` | 報酬の額 | 同 1項4号 | ○ | ○ | 常に |
| `fee_payment_terms[]` | 報酬の支払の時期 | 同 1項4号 | ○ | ○ | 常に。**回数ごとに「時期・金額」を持ち、1 回以上。合計が `fee_amount` と一致すること**（§6.9 の 11） |

| `subcontracts[]` | 委託に係る業務の概要・受託者の氏名又は名称・受託者に係る建築士事務所の名称及び所在地 | 同 6号 | △ | △ | `has_subcontract` が真のとき。**3 項目すべて** |

| `work_type_content_method` | 設計又は工事監理の種類、内容及び方法 | 同 **8号** | ○ | **—** | 常に（契約書のみ） |
| `contract_date` | 契約の年月日 | （法定外。§4.4） | ○ | — | 常に |
| `counterparty_name` | 相手方の氏名又は名称 | （法定外。§4.4） | ○ | ○ | 常に |
| `counterparty_address` | 相手方の住所 | （法定外。§4.4） | ○ | ○ | 常に |
| `counterparty_is_building_owner` | 相手方が建築主か | （判定用。印字しない） | ○ | ○ | 常に |
| `attachments[]` | 別紙目録（受領した図面・資料の名称と受領日） | （任意） | 任意 | 任意 | **必須にしない** |

○＝必須検証の対象、△＝条件付きで必須、任意＝空でよい、—＝その書類には載せない。

> **`architects[]` は配列です。** 複数の建築士が従事することがあり、各要素が
> 「氏名・資格区分・登録番号・構造設計一級／設備設計一級の別」を持ちます。
> **1 名も登録されていない状態を通してはなりません**（1項3号の記載が空になる）。

> **受領図面は PDF に結合しません。** 図面はメールに添付するか Drive のフォルダで共有し、
> 契約書には**目録（名称と受領日）だけ**を載せます。

> **この表は法令そのものです。だから土台（リポジトリ）に置きます。**
> **`backend/app/contract_base.json`** が単一の情報源で、**改正への追従はコードのレビューを
> 経ます**——法定記載事項が増減する変更は、そうあるべきものです。
> **重ねが足すのは、事務所固有の項目・注記・並び・文言・プレースホルダー名・書類の構成**で、
> **そちらは本書に書きません。**

### 4.2 定義の形

証明書ツール（`structural_cert_mapping.json`）の形をそのまま踏襲し、**根拠条文を
データとして持たせます**。コメントではなくデータにするのは、**画面のチェック表と
エラーメッセージにそのまま出すため**です。

```jsonc
// contract_base.json（リポジトリ・公開）— 法令が要求するところまで
{
  "key": "work_period",
  "label": "設計又は工事監理の実施の期間",
  "law_ref": "規則17条の38第7号",
  "documents": ["contract"],          // 重説書面には載せない（22条の2の2 の引用外）
  "required": true
}
```

```jsonc
// 重ね（Drive・非公開）— 事務所の書面ではどう書くか
{
  "key": "work_period",
  "label": "…",                       // 事務所の言い回しに変える
  "section": "…",                     // どの節に、何番目に置くか
  "placeholders": ["{{…}}"]           // 雛形のどこに入るか
}
```

- 各項目が `documents` で**どの書類に載るか**を持ち、**必須検証はその書類の集合に対してのみ**行う
- **土台が必須にしている項目を、重ねで任意にはできません**（発行時に落ちます）。
  **厳しくする方向（任意 → 必須）は通します**（[external-resources.md §6](external-resources.md)）
- 記載事項の改正は**土台を直す**（コードのレビューを経る）。文言・並び・雛形の改訂は
  **重ねを直して発行する**（デプロイは要らない）
- 画面側に項目定義を写さない。`/config` が合成後のルールから導出して配信する（portal の作法）
- **事務所固有の文言をコードに持ちません。** 見出しもエラー文も定義から出ます

### 4.3 記載漏れを 3 段階で止める

**① 入力の必須検証（サーバー側）** — 欠けていれば **400** を返し、PDF を作らせません。
エラーメッセージには**根拠条文を添えます**。

```
次の項目を入力してください: 報酬の支払の時期（法22条の3の3第1項4号）、
設計又は工事監理の実施の期間（規則17条の38第7号）
```

**② 雛形の検証（発行時と生成時の 2 回）** — **発行のときに、雛形の本文を読んで
必須項目のプレースホルダーが実在するかを照合します**（[external-resources.md §4](external-resources.md) の 7）。
照合に落ちた重ねは発行できません。それでも**雛形は発行後に編集できてしまう**ので、
生成時にも `replaceAllText` の `occurrencesChanged` を見て、
**必須項目のプレースホルダーが雛形に 1 つも無かった場合は 409 で失敗させます。**

> **証明書ツールは、ここを警告にとどめています**（`missing_placeholder_warnings`）。
> **契約書では失敗させます。** 警告のまま作らせると、法定記載事項が印字されていない
> 契約書が出来上がります。それは監督処分の対象になる書面です。
> 任意項目（別紙目録など）のプレースホルダーが無い場合は、従来どおり警告でよい。

**③ 法定記載事項チェック表（画面）** — 各行が「根拠条文 ／ 記載事項 ／ 入力済みか」を示す
常設の一覧を置きます。**この表がそのまま「何を漏らしていないか」の説明になります。**

### 4.4 法定外だが書面として必要なもの

- **`contract_date`（契約の年月日）を空で作らせません。** 改正法附則第4条により、
  新法22条の3の3は**施行日以後に締結される契約**に適用されます。施行日をまたぐ案件が
  あるため、**いつ締結したかが適用法令の判定に直結します**
- **相手方の氏名・住所** — 誰との契約かが書面から読めなければ書面として成立しません

### 4.5 重説書面には「説明の実施記録」欄を組み込む

**法24条の7が求めているのは書面の交付ではなく「説明」です。** 書面を渡しただけでは
義務を果たしたことにならず、管理建築士等による説明と**建築士免許証の提示**（同条2項）が
必要になります。システムから実施記録の機能を落とした以上、**記録は書面そのものに持たせます。**

重説書面の末尾に、説明の年月日・方法（対面／ビデオ通話）・説明した建築士（氏名・資格・登録番号・
管理建築士か）・免許証の提示方法・**IT重説の遵守6項目のチェック欄**・建築主の署名欄を置きます。
**この 1 枚で、交付義務の履行（書面）と実施の記録が揃います。**

- 遵守6項目は国交省の IT重説実施マニュアルが定めるものをそのまま写す
- 対面の場合、6項目の欄は印字しない（`method` が `in_person` なら雛形の該当ブロックを空にする）
- **実施記録の欄は空欄で印字するのが既定です。** 重説書面は「あらかじめ」交付するもので、
  説明の実施日は書面の作成日より後になります。実施後に記録を埋めた版を作りたい場合は、
  PDF を開き直して入力し、**別名で保存**します（原本を上書きしない）

### 4.6 変更契約書

**原契約の PDF を開いて作ります。**

```
[開く] → 原契約PDF → 入力が復元される
                    → 変更する項目だけを直す
                    → [変更契約書を作る]
                    → 変更前／変更後の対照表が差分から自動で作られる
```

- **差分が空なら作らせない**（変更のない変更契約書は書面として意味がない）
- 原契約の PDF は上書きしない。変更契約書は別ファイルとして保存する
- 変更契約書にも**変更後の完全な入力**が埋まるので、次の変更はそこから作れる
- 承諾は原契約のときのものを流用できる（撤回されていない限り）。重説は原契約時に
  実施済みであれば再実施は要らない

> **PDF を保存形式にした設計が、いちばん効くのがここです。** 原契約の入力が手元に
> 無ければ、変更契約書は毎回すべて手で書き直すことになります。

## 5. 「何が必要か」の判定 — 3 つの義務を同じフラグで扱わない

**条文ごとに適用の相手方が違います。**

| 義務 | 条文上の相手方 |
| --- | --- |
| 書面の相互交付（法22条の3の3第1項） | 「契約の**当事者**は」— 建築主に限らない |
| 重要事項説明（法24条の7第1項） | 「**建築主と**締結しようとするとき…当該**建築主**に対し」— **建築主に限る** |
| 見積書（法24条の10・**努力義務**） | 「**設計等の業務**に係る契約」— 調査・鑑定を含む。書面契約義務より広い |

元請け設計事務所から受託する場合、**書面の相互交付は必要だが重要事項説明は不要**になります。
**フラグ 1 つに畳まず、判定関数として書きます。**

```python
def requires_important_matters(contract_type: str, counterparty_is_building_owner: bool) -> bool:
    """重要事項説明の要否（法24条の7第1項:「建築主と締結しようとするとき」）"""
    return contract_type in _MAY_REQUIRE_IMPORTANT_MATTERS and counterparty_is_building_owner
```

| 入力 | 書面の相互交付 | 重要事項説明 | 見積書 |
| --- | --- | --- | --- |
| 設計受託・相手方＝建築主 | **必要** | **必要** | 推奨 |
| 設計受託・相手方＝元請け設計事務所 | **必要** | **不要** | 推奨 |
| 工事監理受託・相手方＝建築主 | **必要** | **必要** | 推奨 |
| 耐震診断 | 不要 | 不要 | 推奨（告示第670号） |
| 調査・検査、手続の代理 | 不要 | 不要 | 推奨（告示なし） |

**画面の反応**

| 判定 | 挙動 |
| --- | --- |
| 書面の相互交付が必要 | 契約書の**法定記載事項を必須検証**する。欠けていれば**PDF を作らせない** |
| 重要事項説明が必要 | 重説書面のタブを出し、未作成なら契約書の画面に警告を出す。ただし**契約書の生成はブロックしない** |
| 重要事項説明が不要 | 重説のタブを**出さない**。**「作れ」と促さない**（義務がない） |
| 見積書が推奨される | 「報酬の算定の根拠を示す見積書は努力義務です」と**警告のみ**。ブロックしない |

> **義務がない場面で書類の生成を止めてはなりません。** 安全側に倒すのは
> 「義務があるかもしれない」ときであって、「義務がないと条文で確認できた」ときではありません。
> 重説を義務のない相手に強制すると、実務を止めるだけになります。
>
> **努力義務をブロック条件にしません。** 法24条の10は努力義務であり、監督処分の対象
> （法26条2項1号）の列挙にも含まれていません。**見積を作っていなくても契約書は作れます。**

## 6. 見積り（報酬の算定）— 告示は土台、オリジナルは重ね

**告示に書いてあることはリポジトリに置きます。隠しません。** 別表も難易度係数も官報で
公開されており、**リポジトリに置いて原文と突き合わせるテストで固定するほうが安全**です
（[external-resources.md §1](external-resources.md)）。

**非公開にするのは、事務所が独自に決めた係数とロジック**——独自の補正、加算、値引き、
最低報酬、独自の端数処理、そして書式と文言です。これらは Drive で管理し、
**告示による算定額の「後ろ」に重ねます**（§6.5）。

```
      土台（リポジトリ・公開）                     重ね（Drive・非公開）
      ─────────────────────────                 ─────────────────────
      別表 → 難易度係数 → 費目の積算  ──→ 告示による算定額 ──→ 独自の補正・加算・値引き ──→ 提示額
      ↑ CI で原文と突き合わせる                    ↑ ここが境界      ↑ 発行するだけで変えられる
```

計算は `core/`（Rust → wasm）に置き、**画面とサーバーが同じ実装・同じ土台を動かします**
（必要壁量ツール・面材張り大壁ツールと同じ作法）。画面は入力のたびに金額を出し、
内訳書を生成するときにサーバーが**同じ `.wasm` と同じ版の重ね**で計算し直して突き合わせます。

**告示の原文を取得し、算定方法・費目の構成・別表・難易度係数・略算方法の適用範囲を
確定させました**（→ §10 で contract 側の未確定事項 C として起票されていたもの）。
以下は原文に基づきます。一次ソースは §12。

> **告示だけでは見積りは作れません。** 面積が別表の刻みに乗らない、基本設計だけを受託する、
> 値引きを業務ごとに割り付ける——**条文が答えを持たない場面**が実務には並びます。
> **日事連の JAAF-MST 2024（業務報酬算定システム RESA-6）が、同じ告示のもとで
> それらをどう決めているかを読み、設計に反映しました**（§6.9）。
> **採った数値の一次ソース照合はまだ済んでいません**（§10 の G）。

### 6.1 算定方法（令和6年国土交通省告示第8号）

```
業務報酬 = 業務経費 + 技術料等経費 + 消費税に相当する額          （告示 第一）

業務経費 = 直接人件費 + 特別経費 + 直接経費 + 間接経費           （告示 第二）
  直接人件費  … 業務に直接従事する者の人件費
  特別経費    … 出張旅費、特許使用料その他、建築主の特別の依頼に基づく費用
  直接経費    … 印刷製本費、複写費、交通費等
  間接経費    … 事務所を管理運営していくために必要な費用のうち当該業務に係るもの

技術料等経費 … 業務において発揮される技術力、創造力等の対価      （告示 第三）
```

**略算方法**（告示 第四）は、業務経費のうち 2 つを次のように置き換えられます。

```
直接人件費         = 標準業務人・時間数 × 一人・一時間当たりの人件費   （第四 イ）
直接経費 + 間接経費 = 直接人件費 × 1.1（標準）                        （第四 ロ）
```

**この 1.1 は告示に書かれた値です**（第四ロ「一・一を標準とする倍数」）。
直接経費及び間接経費が通常の場合に比べ著しく異なる場合は、倍数を調整できます（同 5項）。

> **技術料等経費に「率」の規定は告示にありません。** 告示第三は「技術力、創造力等の対価」と
> 定めるだけで、算定式を置いていません。技術的助言も「個別の事情に応じて、契約前に
> 当事者間の協議を行い、定められるのが適切」としています。
> **したがって技術料等経費率は事務所の設定値であり、「告示による」と書いてはなりません**（§6.5）。

別表が式から作られている以上、**補間は別表の再現にならない**ためです。

### 6.4 略算方法が使えない場合

**告示と技術的助言が明示的に排除している場合があります。検知して、略算方法に倒さないこと。**

| 場合 | 根拠 |
| --- | --- |
| **床面積の合計が別表の最小値を下回る／最大値を上回る** | 告示 第四 ただし書。技術的助言 5(1)「調査対象外の規模である」 |
| **増改築、修繕・模様替、設計変更** | 技術的助言 5(1)。標準業務人・時間数は**新築の業務量**を示している |
| 複数の建築物の類型が複雑に混在する建築物 | 同上 |
| 社寺、教会堂、茶室等の特殊な建築物 | 別添二（注）1。**本表に含まれない** |
| 標準設計による場合、複数の建築物について同一の設計図書を用いる場合、設計内容が特に芸術的性格が強い場合、極めて特殊な構造方法等を採用する場合 | 告示 第一、技術的助言 2 |
| **建築物に関する調査又は鑑定その他の業務** | 技術的助言 2「業務報酬基準の対象外」 |
| **調査・企画業務、確認申請等の手続その他の業務** | 標準業務内容の外。**別途の業務として人・時間数を積む**（§6.9 の 5） |

**土台の `guards` に条件として書きます。** **画面の挙動**: 略算方法が使えないと判定したら、**その旨を出して実費積上げのモードに切り替え、
内訳書に「告示の略算方法による」と印字しません。** 根拠のない準拠表示をしないためです。
たとえば戸建住宅で 320㎡ の新築は、別表第13〜15 の最大値 300㎡ を上回るので略算できません。

> **下限を下回るとき（戸建住宅で 100㎡ 未満）は、止めずに参考値を出します。**
> 100㎡ 未満の住宅は事務所の主力で、そのたびに手が止まるのでは道具になりません。
> **別表の最小値（100㎡ の値）で頭打ちにした参考値を出し**、「告示の略算方法による」とは
> 印字せず、**実費積上げのモードで内訳書を作ります**（先行実装も第13〜15類では同じ
> 頭打ちの扱いをしています。§6.9 の 1）。**上限を上回るときは参考値も出しません**——
> 外挿は根拠が無く、頭打ちのように「安全側」とも言えないからです。

**一部の業務のみ行う場合**は、標準業務人・時間数から**行われない業務に対応した業務人・時間数を
削減**します（告示 第四 3項）。これには総合・構造・設備を個別に行う場合だけでなく、
**基本設計のみ・実施設計のみを行う場合**を含みます（技術的助言 5(3)）。
**標準業務内容に含まれない追加的な業務**は、対応する業務人・時間数を**付加**します（同 4項）。

**削減と付加は、画面では 3 つの入力になります**（先行実装に倣う。§6.9 の 2〜4）。

| 入力 | 何をするか |
| --- | --- |
| **業務分野の選択**（総合／構造／設備） | 選ばれなかった分野の人・時間数を落とす |
| **設計業務の範囲**（基本設計／実施設計） | 片方だけのとき**業務比率**を掛ける（§6.9 の 2） |
| **業務量の増減率**（基本設計／実施設計／工事監理 ごとに %） | 成果物を絞った・増やしたことを率で表す。**根拠は業務範囲リストで示す**（§6.9 の 4） |


### 6.5 事務所オリジナルの係数とロジック（重ね）

**告示による算定額の後ろに、事務所が決めたものを重ねます。** 重ねは Drive で管理し、
検証して発行します（[external-resources.md §6](external-resources.md)）。
**コードの変更もデプロイも要りません**——単価の見直しも、値引きの規則の追加も、
**発行するだけ**で本番に出ます。

| 重ねでできること | 例 |
| --- | --- |
| **独自の表を持つ** | 得意先の区分ごとの係数、地域係数、過去の実績からの補正 |
| **独自の手順を足す** | 加算（遠方・急ぎ）、値引き、最低報酬、独自の端数処理 |
| **独自のガードを置く** | 「この条件では受注しない」「この額を下回るときは警告する」 |
| **内訳書に出す行と文言を決める** | どの行を、どの順で、どう書くか |
| **告示の対象外の業務のルールを丸ごと書く** | 調査・鑑定・検査・手続の代理（土台が無いので、最初から書ける） |

```jsonc
// 形を示すための架空の例。実在の係数・値ではない
{
  "extends": "kokuji8",
  "set":    { "…": 0 },
  "tables": { "own_a": { /* … */ } },
  "steps": [
    { "id": "own_b", "after": "kokuji_amount", "label": "…", "expr": "step.… * lookup(own_a, in.…)" }
  ],
  "guards":    [ { "when": "…", "message": "…", "mode": "warn" } ],
  "print":     [ { "step": "own_b", "label": "…" } ],
  "selftests": [ { "in": { /* … */ }, "expect": { /* … */ } } ]
}
```

**差し込めない場所が 1 つだけあります**——**告示による算定額より前**です。
別表や難易度係数の値を書き換えることも、そこまでの手順を差し替えることもできません
（発行時に落ちます）。**告示が事務所に委ねている値**（人件費単価・直接経費＋間接経費の
倍数・技術料等経費率）は **§6.6 の設定値として与えられる**ので、手順を触る必要がありません。

> **これは制約ではなく、書面の要請です。** 内訳書は「告示による算定額」と「提示額」を
> 分けて印字します（§6.8）。**書面で分けるものを、計算でも分けて持つ**というだけのことです。
> 混ぜられるようにすると、**「告示による算定額」が何を指すのか説明できなくなります。**

**重ねの正しさは、重ね自身が持つ自己テストで守ります**（§9.2）。
**公開 CI には事務所の係数が 1 つも登場しません。**

### 6.6 事務所の設定値（Firestore）

**告示に定めのないものは、すべてここに置きます。** 告示の値と混ぜません。
式からは `set.<キー>` で読みます（重ねが要求するキーの宣言は §6.5）。

> **値は Firestore、組み立ては重ね。** 画面から編集したい**数値**はここに置き、
> **その数値をどう使うか**（どの手順で、何に掛けて、どの行に出すか）は重ねが持ちます。
> どちらも非公開で、**変えるのに再デプロイが要らない**という性質も同じです。
> 分けているのは、単価の改定に発行の操作を要求したくないからです。

| キー | 内容 | 告示に定めがあるか |
| --- | --- | --- |
| `personnel_unit_price` | 一人・一時間当たりの人件費 | **なし**（事務所の実態） |
| `overhead_multiplier` | 直接経費＋間接経費の倍数 | **ある**（1.1 標準。調整可） |
| `technical_fee_rate` | 技術料等経費率 | **なし**（協議事項） |
| `adjustment_factor` | 事務所の補正係数（既定 1.0） | **なし**。難易度係数（§6.3）とは別 |
| `minimum_fee` | 最低報酬額 | **なし** |
| `tax_rate` | 消費税率 | — |
| `tax_mode` | 外税／内税 | — |
| `rounding` | 端数処理の位置と方向 | **なし** |
| `line_rounding_unit` | 業務ごとの金額の丸め単位（既定 1,000 円） | **なし**（§6.9 の 9） |

**確定させた設計上の決めごと**（いずれも告示に定めがないため、本書で決める）:

| # | 決めごと | なぜ |
| --- | --- | --- |
| **① 人件費単価は 1 つ** | 技術者区分（主任技術者／技術者／技術員）ごとに持たない | 別添三 9項が「一級建築士として2年又は二級建築士として7年の経験を有する者」を前提に時間数を定めている。区分ごとの単価を掛けると、告示が想定していない値になる。**ただし略算方法によらない実費積上げでは区分ごとに積む**（§6.9 の 14） |
| **② 床面積は直線補間する** | 別表の隣り合う 2 点を直線で結んで補間する | 別表は 100/150/200/300㎡ の離散点で、128㎡ の住宅は必ず点の間に落ちる。**告示は補間方法を定めていない**ので、**内訳書に「別表の値を直線補間した」と明記**し、告示による値と区別する。**補間の結果は丸めない**（0.5 人・時間が出てよい。丸めるのは §6.9 の 4 の増減率を掛けた後の 1 回だけ） |
| **③ 技術料等経費率は直接人件費に掛ける** | 基数は設定値（`technical_fee_base`）にし、**既定は直接人件費**。**特別経費には掛けない** | 告示第三に算定式が無い以上、基数も事務所が決めることになる。**先行実装（RESA-6）が直接人件費を基数にしている**ので既定をそこに合わせる（§6.9 の 10）。**内訳書に基数を印字**し、「直接人件費の 10%」と読めるようにする。特別経費は出張旅費・特許使用料等の実費（告示 第二ロ）であり、実費の立替に技術料の上乗せを掛ける説明が立たない |
| **④ 難易度係数と補正係数を別の行に出す** | 内訳書で別々に印字する | 前者は告示の一部、後者は事務所の判断。混ぜると「告示による算定額」が説明できなくなる |
| **⑤ 最低報酬額が算定額を上回るときは最低報酬額を採る** | その旨を内訳書に印字する | 採った理由が書面から読めないと、法22条の3の4 の説明に使えない |
| **⑥ 費目を 1 つの係数に畳まない** | 直接人件費・直接経費＋間接経費・技術料等経費を**別々の行**として持ち、印字する | 先行実装は 3 つを「経費係数」（＝1＋1.1＋技術料率）に畳んで `人・時間数 × 単価 × 係数` の 1 行で出す。**計算は速いが、内訳書から費目が消える。** 法22条の3の4 の説明に使う書面で、告示第二の費目が読めないのは割に合わない（§6.9 の 10） |
| **⑦ 値引きは業務ごとに按分する** | 総額の値引きを各業務の金額へ按分し、丸め単位（既定 1,000 円）で丸め、**差額は最後の行で吸収**する | 見積書は業務ごとの金額を並べる。按分しないと**行の合計と総額が合わない書面**になる（§6.9 の 9） |

> **按分は土台の手順として実装します。** 式の評価器にはループがありません
> （[external-resources.md §7](external-resources.md)）。業務の行数は入力で変わるので、
> **重ねが式で書けるものではありません。** 重ねから与えるのは
> **丸め単位と、按分の対象にする行**（立替金は対象外）だけにし、
> **按分そのもの・端数の吸収は土台が持ちます**。

**金額は円の整数で確定させ、浮動小数点を使いません。** 途中の値は有理数で持ち、
**丸めは `round` を書いた手順でだけ起こします**（[external-resources.md §7](external-resources.md)）。
端数処理の位置と方向は設定値とし、**内訳書に明記します**。表示のフォーマットは表示層で行い、
計算層は丸めた整数のまま扱います（`core/src/format.rs` の作法）。

```
  ■ 立替金（報酬に含まない）
    R1 消費税を加算するもの（確認申請手数料 …）
    R2 消費税を含んでいるもの（交通費 …）— 二重に課税しない
  ■ 報酬の支払の時期（法22条の3の3第1項4号）
    委託契約時 … ／ 基本設計完了時 … ／ 工事着手時 … ／ 業務完了時 …
    （合計は業務報酬と一致していること。§6.9 の 11）
```

補正の理由は選択式で持ち、印字します（既往の設計図書がある／類似案件の実績がある／
業務範囲を限定している／遠方につき現地確認の回数を要する など）。
**選択肢も、行の並びも、文言も重ねが決めます**——コードには書きません。

> **立替金を報酬に混ぜません。** 確認申請手数料のような立替は、
> **消費税を加算するもの（R1）と、すでに含んでいるもの（R2。交通費など）に分けて持ちます。**
> 分けないと、**税を二重に載せた請求書**が出ます（先行実装が分けている理由もこれです。§6.9 の 8）。

**補正係数が 1 を大きく下回るときは警告を出します**（重ねの `guards` の `warn`）。法22条の3の4 は「報酬の基準に準拠し、
及び見積書の内容その他の事情を考慮して、適正な委託代金で契約を締結するよう努めなければ
ならない」と定めます。**ブロックはしません。** 正当な理由がある場合は当然にありえます。
**理由を書かせることに意味があります。**

告示の対象外の業務（調査・検査・手続の代理）は、**重ねだけで書いたルール**で同じ形の内訳書を作り、
**「告示に準拠」とは書かず**、「業務報酬基準の告示が定められていない業務であるため、
当事務所の積算による」と明記します。

> 本ツールが作るのは**内訳書**です。**見積書そのもの（宛名・件名・金額のある書式）は、
> 別のツールとして先に実装しました**——`quotation-formatter`（README「見積書 作成ツール」）。
> 本ツールが動くまでの繋ぎとしてマネーフォワード クラウド請求書の画面で作る想定でしたが、
> 過去の見積書がすべて同じ書式で、明細を並べて消費税を足すだけの帳票だったため、
> **重ねの仕組みを待たずに作れる**と分かったからです。
>
> **2 つのツールの関係**（重複ではありません）:
>
> | | `quotation-formatter`（実装済み） | 本ツール（未実装） |
> | --- | --- | --- |
> | 作る書面 | **見積書**（宛名・件名・明細・消費税） | 契約書・重要事項説明書・変更契約書・**業務報酬内訳書** |
> | 報酬の算定 | **告示第670号の略算**（耐震診断・耐震補強設計）と、手入力の単価 | 告示第8号・第670号の**費目まで積む**算定と、事務所の重ね |
> | 事務所固有のもの | 定型文・単価を**共有設定**に置く | **重ね**（Drive）に置く（§6.5） |
>
> 見積書ツールが持っているのは**告示第670号の別表と費目**（`core/src/kokuji670.rs`）までで、
> 補正・値引き・按分・立替金の R1／R2 は持ちません。**本ツールの Phase 2 が要らなくなった
> わけではありません。** 逆に、別表と費目の Rust 実装・整数での金額の扱い・
> 摘要の組み立てと共有設定の分け方は、**Phase 2 がそのまま土台にできます**。

### 6.9 先行ツール（JAAF-MST 2024 / RESA-6）から取り入れたもの

**同じ告示で見積りを作る道具は、すでに業界にあります。** 一般社団法人日本建築士事務所
協会連合会（日事連）の **JAAF-MST 2024**（Excel）で、報酬算定を担うのが
**業務報酬算定システム RESA-6**（令和6年告示第8号準拠）です。**告示の条文だけからは
決まらないところを、この実装がどう決めているか**を読み、設計に反映しました。

> **RESA-6 は二次情報です。** 数値も手順も**告示の原文ではありません**。
> ここに書いたのは「先行実装がこうしている」という事実であって、**根拠ではありません。**
> **土台（`core/rules/`）に入れてよいのは原文と突き合わせたものだけ**で、
> 照合が済んでいないものは §10 の **G** として起票し、**照合するまで実装しません**
> （調査の時点で国土交通省のサイトへ到達できず、照合は未了です）。

| # | 先行実装がしていること | 本ツールでどうするか |
| --- | --- | --- |
| **1** | **任意面積への対応**。第13〜15類（戸建住宅）は別表の隣接点を直線で結んで補間する。**下限（100㎡）未満は最小値で頭打ち**、**上限（300㎡）超は算定しない**。第1〜12類は補間せず `A = a × S^b`（官庁営繕の積算基準の式）で求め、別表と同じ丸め（1,000以上は下2桁、100以上は下1桁を切り捨て）を掛ける | **採る**（§6.2・§6.4・§6.6 ②）。**戸建住宅の補間だけを実装**し、非住宅の式は係数を原文で確かめてから |

## 7. データの持ち方 — **PDF が保存形式である**

**データベースを持ちません。** 契約の内容は PDF の文書情報に埋め込みます。

```
フォーム入力 ──→ 雛形の複製に置換 ──→ PDF書き出し ──→ 入力を文書情報へ埋め込む
                                                          │
                                                          ▼
                                                     Drive へ保存
                                                          │
     フォームへ完全復元 ◀── 文書情報を読む ◀── PDFを開く ─┘
```

```json
{
  "documentKind": "…（種別は重ねが決める。コードは知らない）",
  "fields":  { "…法定記載事項と任意項目…" },
  "choices": { "…契約種別・事務所の別・資格区分…" },
  "fee":     { "…報酬算定の入力と結果…" },
  "rules":   { "base": "…", "overlay": "…", "publishedAt": "…" },
  "templateRevision": "…",
  "generatedAt": "…"
}
```

- 文書情報は **ASCII に収まるよう JSON 文字列としてエスケープして持つ**（証明書ツールの作法）
- **氏名・住所を含みます。** 保存先フォルダの共有設定が個人情報の境界になります
- **`rules` が、どの版の土台とどの版の重ねで作ったかを指します**
  （[external-resources.md §9](external-resources.md)）。開き直したときに現在の版と
  違えば画面に出しますが、**再計算はしません。金額は PDF に入っている値が正です**

| 要件 | どう満たすか |
| --- | --- |
| **締結時点の契約条件を固定する** | 入力そのものが PDF に入る。**マスタを参照しないので、事務所名や登録番号を更新しても過去の契約書の再現性は壊れない** |
| **どの規則で算定したかを後から示す** | 土台はリポジトリの版から、重ねは `revisions/<hash>` から引ける |
| **変更契約を原契約から作る** | 原契約 PDF を開けば入力が復元される（§4.6） |
| **二重管理をしない** | 成果物が 1 つ（PDF）だけになる |
| **本ツール以外で作った PDF も扱える** | 本文のレイアウトから推定して読み込む（証明書ツールと同じ。推定であることを画面に出す） |

**印字する値はマスタを参照せず、入力された値を使います。** 事務所名・建築士の登録番号は
共有設定に持ちますが、**それは初期値です。** 設定を後から変えても、過去の契約書は変わりません。

### 7.1 Firestore に置くもの

portal の `settings_store` と `resource_store` を使います。
どちらもチャンネル（本番／開発／PR プレビュー）で分かれます。

**`tool_settings/contract-formatter`**（人が画面から編集する値）

| キー | 内容 |
| --- | --- |
| `resource_folder_id` | **設定フォルダ**（雛形と定義の置き場所）。Picker で選ぶ |
| `office` | 事務所の情報（名称・所在地・一級／二級／木造の別・開設者名）**＝フォームの初期値** |
| `architects` | 所属建築士（氏名・資格区分・登録番号・管理建築士か）**＝同上** |
| `fee` | 報酬算定の設定値（§6.5）。式が `set.*` で読む |

**`tool_resources/contract-formatter`**（発行の結果。人が直接編集しない）

| | 内容 |
| --- | --- |
| 目印 | 発行済みの版のハッシュ・発行者・発行日時・自己テストの結果 |
| `revisions/<hash>` | **重ねの中身そのもの**（不変。過去の版も残る） |

> **雛形のファイル名を 1 つずつ持ちません。** どの書類がどの雛形を使うかは重ねにあり、
> Firestore が覚えているのは**フォルダ 1 つと、発行した版**だけです。
> **書類が増えても、ここのキーは増えません。**

### 7.2 ファイル名 — 電帳法に効く唯一のところ

**保存は事務所の手元（Drive）で行うため、システムは電子帳簿保存法の要件充足の主体に
なりません。** 真実性は**規則4条1項4号の事務処理規程**、可視性は**小規模事業者の特例＋
ファイル名規則**で満たします。

**システムができるのは 1 つだけ —— ファイル名を `YYYYMMDD_取引先名_金額.pdf` の形で
既定として組み立てること。** そのまま保存すれば検索要件の備えになります。

> ⚠ **事務処理規程はリリースのブロッカーです。** 規程が未整備のまま運用を始めると、
> 真実性の要件を満たす手段がゼロになります。**規程はコードより先に要ります。**

### 7.3 交付の技術基準を壊さないこと

規則17条の39第2項1号・22条の2の3第2項1号は「**出力することにより書面を作成できること**」を
求めています。**これは法令要件です。生成する PDF に権限制限（印刷禁止・テキスト抽出禁止）を
かけてはなりません。** PDF 生成のオプションを変えるときは、この節を読むこと。

同 2項2号は「改変が行われていないかどうかを**確認**することができる措置」を求めます
（重説書面の規則22条の2の3第2項2号は「改変を**防止**するための措置」と文言が異なります）。
**PDF 形式での交付でこれを満たすというのが国交省の示す運用**であり、上乗せの措置は取りません。

## 8. セキュリティ

portal の既存の作法に従いつつ、契約書という書類の性質から来る上乗せがあります。

- **PII をログに出さない** — 氏名・住所・メールアドレス・電話番号・**建物の所在地**
- 認証・認可は portal のまま（Clerk セッション JWT の検証 → 許可ドメイン確認 →
  代理アクセストークン）。**雛形の取得も保存も、常に実行ユーザー本人の権限の範囲**で行われる
- **アップロードサイズの上限**は portal の PDF ツールと同じ 20MB
- **設定フォルダ・契約書類フォルダの共有設定が実質的な境界です。**
  「リンクを知っている全員」の使用を規程で禁止する
- **設定フォルダの編集権限は管理建築士に限る。** これがそのまま
  「重ねを発行できる人」になります（[external-resources.md §4](external-resources.md)）。
  **portal 側に権限の仕組みを作りません**
- **雛形の改訂日と、使った土台・重ねの版を書面と PDF に残す**（§4・§7）
- **テストのフィクスチャに実在の氏名・住所を使わない。値も架空のものにする**

### 公開リポジトリであることから来る制約

**このリポジトリは公開です。** 何を入れ、何を入れないかを取り違えないこと。

| | 入れる | 入れない |
| --- | --- | --- |
| 報酬算定 | 告示の別表・難易度係数・費目・略算方法（**原文と突き合わせるテストつき**） | **事務所独自の係数・補正・値引き・最低報酬・独自の端数処理** |
| 書式 | 法定記載事項のキー・必須条件・根拠条文 | **事務所固有の項目・並び・文言・プレースホルダー名・条項** |
| 設定値 | — | **単価・税率・補正係数**（Firestore） |
| 例・テスト | 架空の重ね（`overlay-sample`） | **実在の氏名・住所・金額** |

**非公開の範囲**（誰にどこまで見えるか）と、**利用者には見えてよいと決めたこと**は
[external-resources.md §1・§10](external-resources.md) にまとめてあります。
**「隠したつもりで隠せていない」を作らないため、そこを読んでから実装します。**

> **契約書という書類の重さは、アプリケーションを分けることではなく
> 保存先フォルダの共有設定で担保します。**

## 9. テストで守ること

**守る場所が 2 つに分かれます。** 告示と法令の値はリポジトリにあるので**公開 CI で守れます**。
事務所固有の係数と手順はリポジトリに無いので、**発行時の自己テストで守ります。**

### 9.1 公開 CI

portal の CI に載せます。**これらが通らない変更は入れません。**
重ねが要るテストは `backend/tests/fixtures/overlay-sample/` の**架空の重ね**を使い、
**事務所の値は 1 つも登場しません。**

```
- 報酬  : 告示の別表の値が原文と1つも違わないこと（表を丸ごと突き合わせる）
- 報酬  : 難易度係数が、別表第1の1〜12の2 と 別表第13〜15 で正しく切り替わること
- 報酬  : 複数の難易度係数に該当するとき、すべての倍数が乗じられること
- 報酬  : 床面積が別表の範囲外なら略算方法に倒さないこと
- 報酬  : 別表の刻みの間の面積で、隣接2点の直線補間になっていること（補間の結果を丸めないこと）
- 報酬  : 下限未満は最小値で頭打ちにし、上限超では算定しないこと（§6.4）
- 報酬  : 業務分野・設計の範囲・増減率で人・時間数が減り、切り捨てが1回だけ起きること
- 報酬  : 技術料等経費の基数が設定どおりで、特別経費には掛からないこと（§6.6 ③）
- 報酬  : 値引きの按分後、業務ごとの金額の合計が総額と一致すること（丸め単位を変えても）
- 報酬  : 立替金の R2（消費税を含むもの）に消費税が二重に載らないこと。外税／内税で総額が整合すること
- 必須  : 支払の時期の金額の合計が報酬の額と一致しないとき、警告が出ること
- 報酬  : 告示第670号で検査費の費目が立ち、倍数が 1.0 になること（第8号では 1.1）
- 報酬  : 重ねが無くても、告示による算定額まで出せること
- 報酬  : 同じ土台・同じ重ね・同じ入力から、常に同じ金額が出ること
- 合成  : 別表の値を書き換える重ねが、発行時に落ちること
- 合成  : 告示による算定額より前の手順を差し替える重ねが、発行時に落ちること
- 合成  : 土台が必須にした項目を任意にする重ねが落ち、逆（任意→必須）は通ること
- 合成  : 重ねの手順が、告示による算定額の後ろにだけ入ること
- 必須  : 必須の項目を1つずつ欠いたケースを全件作り、すべて 400 になること
- 必須  : 書類ごとに必須の集合が違うこと（規則17条の38第7号・第8号は重説では必須にしない）
- 必須  : エラー文に、土台が持つ根拠条文がそのまま出ること
- 判定  : 相手方が建築主でない場合に、重説を要求しないこと（両ケースを固定する）
- 判定  : 見積未作成でも契約書が作れること（努力義務をブロックにしていないこと）
- 雛形  : 必須項目のプレースホルダーが無い雛形で、発行が落ちること
- 雛形  : 発行後に雛形からプレースホルダーが消えた場合、生成が 409 になること
- 生成  : 生成したPDFのテキストに、入力した法定記載事項がすべて含まれること
- 往復  : 生成したPDFを解析すると、入力が完全に復元されること
- 往復  : PDF に土台の版と重ねのハッシュが入り、開き直したときに版の違いが分かること
- 変更  : 差分が空なら変更契約書を作らせないこと
- 評価器: 表引き・直線補間・条件・丸めが期待どおりになること
- 評価器: 画面（wasm）とサーバが同じ値を出すこと（既存の verify の作法）
- 評価器: ノード数・深さ・手順数の上限を超える式が**発行時に**落ちること
- 評価器: 未知の識別子・循環参照・0 除算・丸めを通らない出力が発行時に落ちること
- 端数  : 円未満が出ないこと。丸め方向が設定どおりであること
- 発行  : 検証に落ちた重ねが発行されないこと。落ちた理由が場所つきで返ること
- 発行  : 自己テストが1件でも合わなければ発行されないこと
- 発行  : ロールバックで前の版に戻り、実行時の値がその版のものになること
- 未発行: 発行前は 409 で、案内の文面が出ること
```

**「検証を通ったこと」で満足しません。** 検証を通っても雛形に印字されていなければ
意味がないので、**生成した PDF からテキストを抽出して突き合わせるところまで**をテストにします。
ネットワーク（Drive / Docs / Firestore）はフェイクで置き換えます。

テスト名は日本語で書いてよい（portal の既存のテストと同じ）。

```python
def test_報酬の支払の時期が空なら契約書を作れない(): ...
```

### 9.2 発行時（事務所の重ねで回る）

**事務所独自の係数と手順が正しいことは、公開 CI では守れません。**
代わりに**重ね自身が持つ自己テストを、発行のたびに合成後のルールで流します**
（[external-resources.md §8](external-resources.md)）。

```
- 独自の補正・加算・値引きを通した金額が、社内規程から確かめた期待値と一致すること
- 独自のガードが、意図した条件でだけ立つこと
- 告示の対象外の業務のルールが、実費積上げとして期待どおりに動くこと
- 過去の見積り数件を入力したとき、当時の金額が再現されること
```

**1 件でも合わなければ発行できません。** 原本（社内規程・過去の見積り）との突き合わせは
人の作業で、**その結果が自己テストとして残り、発行の記録に「自己テスト N 件 合格」として
付きます。**

### Phase 2 — 報酬算定と業務報酬内訳書（2027-02 〜 2027-03）

**目標**: 同じ入力からは必ず同じ金額が出る。報酬の算定根拠を示せる。

- **告示の土台を `core/rules/` に実装する**（§6）
  - `kokuji8.json` — 別表第1の1〜第15、難易度係数（別添三 3〜8項）、倍数 1.1
  - `kokuji670.json` — 別表第一・第二、検査費、倍数 1.0
  - **別表の値が原文と 1 つも違わないことをテストで固定する**（§9.1）
- **式の評価器を `core/`（Rust → wasm）に実装する**（§6。
  [external-resources.md §13](external-resources.md) の第 1 段）
  - `expr.rs` / `table.rs` / `money.rs` — 式の評価・表引きと補間・有理数と丸め
  - `merge.rs` / `check.rs` — 合成と静的検査（**禁じ手の判定**を含む）
- **報酬算定の重ねを発行する**（独自の補正・加算・値引き・自己テスト。Phase 0-6 で事務所が書く）
- 事務所の設定値（§6.6）を Firestore に置き、画面から編集できるようにする
- **画面が入力のたびに金額を出す。** 内訳書の生成時にサーバーが**同じ `.wasm` と同じ版の重ね**で計算し直して突き合わせる

- 告示の対象外の業務（調査・検査・手続の代理）の実費積上げ（**重ねだけで書く**）
- **業務量の削減と付加**（業務分野の選択・設計の範囲・増減率）と、その根拠となる業務範囲リスト（§6.4）
  - **業務比率（基本設計／実施設計）は §10 の G を照合してから**。照合が済むまでは
    **両方受託の案件だけを対象にする**（比率が要らない）
- **報酬の支払の時期**を回数・時期・金額で入れ、合計と報酬の額の一致を確かめる（§6.9 の 11）
- **値引きの按分と丸め、外税／内税、立替金の R1／R2**（§6.6 ⑦・§6.8）
- **略算方法が使えないときの実費積上げモード**（区分ごとの人日 × 日額単価。§6.9 の 14）

> **法24条の10 は努力義務であり、施行日に間に合わせる必要はありません。**

- **変更契約書**（法22条の3の3第2項）。原契約 PDF を開いて作る（§4.6）
- **契約種別の拡張**: 耐震診断、建築物調査・検査（定期報告等）、手続の代理、その他
  - 種別ごとに「書面相互交付の要否」「重説の適用候補」「見積書の推奨」「適用するルールセット」を切り替える
  - **雛形と重ねを足して発行するだけで済む**ものと、土台・判定（§5）に手が要るものを分ける
- **元請け設計事務所からの受託**（重説は不要・書面相互交付は必要）
- **再委託の記載**（規則17条の38第6号）。相手が建築士事務所の開設者であることを入力必須にする
  （法24条の3第1項）。300㎡超の新築工事では一括再委託でないことの確認項目を出す
  （同 2項。**ブロックはしない**）
- **改正法の施行政省令を反映**（記載事項は土台を直し、文言と雛形は重ねを発行して合わせる）
- 全案件を本ツールへ移行

### 共通のロジックを寄せる作業との関係

**このツールは 5 つめのツールとして、[shared-logic.md](shared-logic.md) の後押しになります。**
そこで挙がっている重複は、**そのまま契約書ツールでも要るもの**だからです。

| shared-logic の項 | 契約書ツールでどう要るか |
| --- | --- |
| 2.1 雛形の設定（フォルダ + ファイル名） | **雛形が 4 つあるが、設定する操作は 1 つ**（フォルダを選んで発行する）。**「同じ段取りを 4 回書き写す」は、重ねの仕組みにしたことで起きなくなりました** |
| 2.2 ファイル名の組み立て | 既定のファイル名 `YYYYMMDD_取引先名_金額.pdf`（§7.2） |
| 2.3 画面とサーバの突き合わせ | 報酬算定を画面と内訳書の生成時に突き合わせる（§6）。**土台の版と重ねのハッシュも突き合わせる** |
| 2.4 条件の評価 | **必須になる条件が法令由来で多い**（`required_when` / `documents` ごとの必須集合。§4.1）。**式の評価器（§6）と同じ語彙で書けるかは、寄せるときに確かめる** |
| 2.5 生成物の引き渡し | PDF の保存と、`/documents/parse` `/documents/parse-drive`（§2） |
| 3.1 入力欄の組み立て | フォームが既存のどのツールより大きい（節が 7 つ。§3） |

> **2.1 の押しは弱くなりました。** 以前の版では「このツールだけで同じ段取りを 4 つ持つ」
> ことが第 1 段の後押しでしたが、**設定フォルダを 1 つ選ぶ形では、雛形の数だけ設定が
> 増えるということ自体がありません。** 第 1 段は既存の 2 ツールのためにやる作業として残ります。

> **寄せる作業を Phase 1 の前提にはしません。**
> shared-logic の順序（第 1 段から第 7 段）はそれ自体で完結しており、
> 契約書ツールの都合で組み替えると、**先回りした一般化**になります
> （shared-logic §5「進め方の決めごと」）。**間に合った段だけ使い、
> 間に合わなければ既存のツールと同じ書き方で書いて、後から寄せます。**

**重ねの仕組みは、寄せる作業とは別のものです。** 第 1〜7 段が
「**すでに 2 か所以上で重なっているもの**を土台へ寄せる」作業なのに対し、
こちらは**新しく足す能力**です。**既存のツールを書き換えません**
（移さない理由は [external-resources.md §12](external-resources.md)）。
どちらを先にやってもよく、互いをブロックしません。

## 12. 一次ソース

**法令・告示は必ず一次ソースに当たります。** 解説記事・業界紙・要約サービスは、
一次ソースを探す手がかりとしてのみ使い、根拠として引用しません。
このツールは法令の条文と告示の別表を**土台に写す**ので、二次情報の誤りはそのまま
「法定記載事項が欠けた契約書」「根拠のない報酬額」になります。
**写したものが原文と 1 つも違わないことは、公開 CI で固定します**（§9.1）。

### 再検証するタイミング

法令は変わります。次のときに条文と突き合わせ直します。

- 改正法の施行期日政令が公布されたとき
- 施行に伴う政省令（施行令・施行規則）が改正されたとき
- **告示が改正されたとき（土台の別表を差し替え、CI の突き合わせを更新する）**
- 年1回（定例）
- **§10 の G が解けたとき**（先行実装から採った数値を原文で照合し、土台へ入れる）

条文の解釈に関わる判断は、**contract 側の
[01-legal-requirements.md](https://github.com/min-nano/contract/blob/main/docs/01-legal-requirements.md)
に反映してから土台と重ねを直します。**
