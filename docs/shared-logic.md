# 共通のロジックをまとめる

このポータルは「土台（portal）＋ ツール」という作りになっています。
ツールが増えるにつれて、**同じことを別々のツールが別々に書いている**箇所が
できてきました。この文書は、それを洗い出し、**どれをどの順で土台へ寄せるか**を
並べたものです。

## 分割はやめました

以前は「ツールを 1 つずつ別リポジトリへ出す」という設計
（`docs/plugin-architecture.md`）を置いていましたが、**取り下げました**。
理由は 2 つです。

* **払うものが大きい。** 土台を直すたびに N 個のリポジトリで追従の PR が要り、
  「全ツールの保存ダイアログの文言を直す」のような横断的な変更が
  リポジトリを跨ぎます。ツールが 4 つの今、これは重すぎます
* **得たかったもの（重複の解消）は、分割しなくても取れる。** 読む範囲を狭める
  ことよりも、**同じロジックが 2 か所以上にある状態を無くす**ほうが直接効きます。
  そしてそれは portal の中だけで完結します

分割の下ごしらえとして入れた **「ツールが自分を名乗り、土台がそれを読んで
組み立てる」という形（マニフェストとルーター）はそのまま使います**。
これは分割のためだけの仕組みではなく、「土台にツールの名前が出てこない」
という線引きそのものだからです（README の「🧩 土台とツール」）。

**フレームワークも作りません。** 3 つのツールを 1 つの汎用エンジン
（レシピの解釈器）にまとめる案も検討しましたが、採りません——今ある 3 つに
合わせた語彙を先に作ると、4 つめが来たときに語彙ごと作り直すことになります。
代わりに、**実際に 2 か所以上で重なっているものだけを、1 つずつ土台へ寄せます**。

## 1. すでにまとまっているもの

新しく線を引くのではなく、**すでにある線を延ばす**話です。現在地はここです。

| | 寄せ先 | 中身 |
| --- | --- | --- |
| 失敗の返し方 | `app/errors.py` の `PortalError` | 全ツールが同じ形（`message` + `status`）。`main.py` のハンドラは 1 つ |
| 認証・代理アクセス・共有設定 | `app/portal_sdk.py` | `require_user` / `delegated_session` / `get_settings` |
| 雛形の設定（Drive の「フォルダ + ファイル名」） | `app/portal_sdk.py` の `Template` | 状態（`status`）・保存（`save`）・未設定の 409（`require`）。ツールが渡すのは**許す種類と文言だけ** |
| ファイル名の規則 | `app/portal_sdk.py` ＋ `src/pdf-file-ops.js` | 「使えない文字を落とす・拡張子を付ける・空なら既定値」。サーバと画面が同じ答えを返すことは `backend/tests/file_name_cases.json` を両方のテストが読んで縛る |
| PDF の保存先と保存 | `app/portal_sdk.py` | `resolve_pdf_destination` / `save_pdf` / `open_drive_pdf` / `read_upload` |
| wasm の配り方 | `app/portal_sdk.py` | `wasm_response`（gzip・ETag・キャッシュ） |
| ツールの名乗り | `Tool` / `tool_router` / `tools/__init__.py` | `main.py` にツールの名前は出てこない |
| 画面の見た目 | `src/styles/`（tokens・base・layout・components） | 色・余白・部品。ツールは生の値を書かない |
| 画面の共通部品 | `src/components/` | ヘッダー・読み込み中・サインインゲート・折り畳み節・PDF のファイル操作欄 |
| PDF のファイル操作 | `src/pdf-file-ops.js` / `src/save-dialogs.js` | 「保存 / 別名で保存 / 未保存の確認」の判断と文言 |
| Picker | `src/google-picker.js` | Drive のファイル選択 |

以下に挙げるのは、**この表に入っていないのに 2 か所以上で同じことをしている**ものです。

## 2. 洗い出し — API 側

### 2.1 雛形の設定（Drive の「フォルダ + ファイル名」）〔第 1 段 · 済〕

> **済**: `portal_sdk.Template` に寄せました（下の記述は寄せる前の状況です）。
> ツールに残るのは `Template(...)` の宣言（種類と文言）と、それを呼ぶだけの
> ルート 2 本です。安全証明書の `GET /settings` は `GET /template` へ揃えました。

現況検査レポートと構造計算安全証明書は、どちらも雛形を Drive に置き、
**ファイルの ID ではなく「親フォルダの ID + ファイル名」**で覚えています
（同じフォルダへ同名で置き直せば、それが自動的に最新版になるため）。

Picker で選ばれた `fileId` を受け取り、**ゴミ箱・種類・親フォルダを確かめて
共有設定へ保存する**という段取りが、`tools/excel_report_formatter.py` と
`tools/structural_cert_formatter.py` に**ほぼ同じ形で 2 つ**あります
（合わせて 90 行ほど）。違うのは**許す種類（.xlsx / Google ドキュメント）と、
違うものが選ばれたときの文言だけ**です。

未設定のときに 409 を返す `_require_template` も同じものが 2 つあります。

**寄せ先**: `portal_sdk`。種類と文言だけをツールが渡す形にします。

> **これとは別に、「事務所オリジナルの係数・ロジック・書式を Drive で管理して、
> リポジトリの土台に重ねる」仕組みを足します**（[external-resources.md](external-resources.md)）。
> **このリポジトリは公開**で、見積書・契約書等の作成ツールには**外に出したい独自のもの**が
> 入るためです（告示や法令に書いてあることは、隠さずリポジトリに置きます）。
> **寄せる作業ではなく、新しく足す能力です。**
> ここで挙げた既存の 2 ツールは**そのまま**で、第 1 段の内容は変わりません
> （移さない理由は external-resources.md §12）。

> **1 か所だけ、応答の形がずれています。** 雛形の設定状態を、
> 現況検査レポートは `GET /template` → `{ configured, fileName }`、
> 安全証明書は `GET /settings` → `{ template: { configured, fileName } }` と、
> **同じものを違う名前・違う形で**出しています。寄せるときに `GET /template`
> の側へ揃えるので、安全証明書の画面が 1 か所変わります。

### 2.2 ファイル名の組み立て〔第 2 段 · 済〕

> **済**: `portal_sdk` の `sanitize_file_name` / `ensure_file_name` /
> `build_file_name` と、画面側 `pdf-file-ops.js` の同じ 3 つに寄せました
> （下の記述は寄せる前の状況です）。画面にも 2 つあった「雛形から既定の
> ファイル名を作る」（`suggestedFileName`）も 1 つになっています。
> サーバと画面がずれていないことは `backend/tests/file_name_cases.json`
> を両方のテストが読んで確かめます。

同じ規則が **4 か所**にあります。

| 場所 | 中身 |
| --- | --- |
| `structural_cert.py` の `_UNSAFE_FILE_NAME_CHARS` / `ensure_pdf_extension` | 正規表現も関数の中身も次と 1 文字違わない |
| `panel_shear.py` の `_UNSAFE_FILE_NAME_CHARS` / `ensure_pdf_extension` | 同上 |
| `wall_quantity.py` の `_sanitize` | **落とす文字が少し違う**（制御文字を落とさない） |
| `src/pdf-file-ops.js` の `sanitizeFileName` / `ensurePdfExtension` | 画面側。「バックエンドの整形と同じ規則」と書いてある |

`default_file_name`（雛形からファイル名を組み立て、空なら既定値へ倒す）も、
証明書・計算書・必要壁量の 3 つにそれぞれあります。

**寄せ先**: `portal_sdk`。「使えない文字を落とす」「拡張子を付ける」
「空なら既定値」の 3 つを 1 つにし、ツールが渡すのは雛形と既定値だけにします。
**画面側の規則がサーバと同じであることは、テストで縛ります**（今は
コメントで「同じ規則」と書いてあるだけです）。

### 2.3 画面とサーバの突き合わせ（verify）

必要壁量と面材張り大壁は、どちらも「画面（wasm）が出した値」と
「サーバが同じ wasm で出した値」を保存のたびに突き合わせます。

`wall_quantity.verify` と `panel_shear.verify` は、**外枠が完全に同じ**です。

* 材料が届かない（古い画面）なら `{checked: False, ok: True, differences: []}`
* `coreVersion` の client / server を並べる
* 差分が無く、かつ版が同じときだけ `ok`
* `differences[:20]` と `omittedDifferences`（`MAX_REPORTED_DIFFERENCES = 20`
  という同じ定数が両方にある）

違うのは**差分の作り方だけ**です（必要壁量は「key → 表示文字列」の突き合わせ、
面材張り大壁は壁と面材の 2 系統）。

**寄せ先**: `portal_sdk`。外枠を土台に置き、ツールは差分の一覧だけを渡します。

### 2.4 条件の評価（この欄は今、入力できるか）

同じことを **2 通りの書き方**でやっています。

| | 必要壁量 | 構造計算安全証明書 |
| --- | --- | --- |
| 書き方 | 宣言的。`visible_when` / `required_when` / `fixed_when` を mapping が持ち、`_condition_met` が判定する | 専用の仕掛け。`depends_on_field`（記入欄が埋まっているときだけ選べる）と `requires_field`（その選択肢のときだけ書ける欄）を `_field_gates` / `_group_is_active` が解く |
| 連鎖 | 無い | ある。`_clear_inactive` が変化の無くなるまで繰り返す |
| 画面側 | `form-logic.js` の `conditionMet` | `form-logic.js` の `fieldDependencies` |

証明書の 2 つの仕掛けは、宣言的な述語で書けます
（`depends_on_field` → 「その欄が埋まっている」、`requires_field` → 「その選択肢が
選ばれている」）。逆に、必要壁量には連鎖の評価がありません（今は要らないだけで、
条件が条件を生む形になれば同じ問題が出ます）。

**寄せ先**: `portal_sdk`（述語の判定と、変化が無くなるまでの評価）。
ただしこれは **mapping の書き換えを伴う**ので、他の項目より重い作業です。
画面側にも同じ判定があるため、**サーバと画面で 1 つずつ**になります
（wasm のように 1 つの実装を共有はできないので、**同じ入力に同じ答えを返すことを
テストで縛る**のが現実的な線です）。

### 2.5 生成物の引き渡し

| | 今 |
| --- | --- |
| ダウンロード（xlsx） | `tools/excel_report_formatter.py` と `tools/wall_quantity_calculator.py` に、`Content-Disposition: attachment; filename*=UTF-8''{quote(...)}` を組み立てる同じ 4 行 |
| Drive へ保存（PDF） | 証明書・計算書の応答 `{mode, fileId, fileName, webViewLink, …}` の組み立てが 2 か所 |
| PDF の読み戻し | `/parse`（アップロード）と `/parse-drive`（Drive）の 2 本が、証明書・計算書で**ほぼ同一**。違うのは解析関数と、既定のファイル名だけ |

**寄せ先**: `portal_sdk`。`save_pdf` の隣に応答の組み立てを置き、
`/parse` 系はルートごと生やせる形にします。

## 3. 洗い出し — 画面側

### 3.1 入力欄の組み立て

`form-dom.js` が 3 つあり（証明書 402 行・必要壁量 350 行・面材張り大壁 886 行）、
**骨格が同じ**です。

* ラベル + `<div class="field-row">` + 入力 + 単位 + 注意書き
* 単位から入力モードを決める（`NUMERIC_UNITS` / `DECIMAL_UNITS` という
  **同じ名前の定数が別々の中身で**それぞれにある）
* 必須の印、入力できない状態の切り替え、節を開いて示す

違うのは型の扱いです（証明書は末尾の 0 を保つため `type=text` のまま、
必要壁量は `type=number` と `step` / `min` を使う）。これは**部品の引数**に
なる違いで、部品そのものを分ける理由にはなりません。

**寄せ先**: `src/components/`。**「節・入力欄・選択肢」までを部品にし、
ツール固有の振る舞いはツールの `main.js` に残します**（部屋の見出しの追従・
和暦の組み立て・釘配列図・出力結果の表など）。

### 3.2 デザインシステムに漏れているツール固有の名前

`src/styles/components.css` に **`.wq-field` と `.cert-field`**（＝必要壁量と
証明書のクラス名）が 14 行ほど出てきます。「デザインシステムにツールの名前は
出てこない」という決めごとが、ここだけ破れています。

**寄せ先**: 3.1 と同じ 1 つの仕事の裏表です。入力欄を部品にすれば、
クラス名は 1 つの汎用の名前になります。

### 3.3 雛形を設定する画面

現況検査レポートと安全証明書の `main.js` に、
「雛形を設定ボタン → Picker → `PUT /template` → 表示の更新 → 未設定なら
送信ボタンを無効化」という同じ流れがあります。2.1 の画面側です。

**寄せ先**: `src/components/`（`pdf-file-ui.js` の隣）。

## 4. まとめないもの（理由つき）

無理に 1 つにすると壊れるものを、先に書いておきます。

### 4.1 xlsx への書き込み — 2 通りのままにする

| | 現況検査レポート | 必要壁量 |
| --- | --- | --- |
| 使うもの | openpyxl（ブックを読み直して書き出す） | `xlsx_fill.py`（zip の中の触る場所だけ書き換える） |
| 失うもの | チェックボックス・図・VML・印刷設定は復元されない | 何も失わない |
| 保護シート | ロックされたセルへは**黙って書かない** | 確認しない |

一見すると `xlsx_fill` へ一本化できそうですが、**できません**。
保護シートの確認は事故ではなく、**意図された仕組み**です——
`mapping.json` の覚え書きに「入力例ブロック（グレーアウトされた最初の部屋）の
セルはロックされたまま維持し、実際の記入ブロックのセルだけ `locked=False` に
設定することで書き込み可否を制御できる」と書いてあり、雛形の作り手が
ロックによって「ここは書くな」を指示しています。しかもこれは
`test_reports.py` の **4 本のテスト**が明示的に守っています。

**選ぶのは雛形の性質です**——「配布物そのものを返す（何ひとつ失えない）」なら
`xlsx_fill`、「書ける場所が雛形側で指示されている」なら openpyxl。

### 4.2 その他

* **NFKC 正規化が 2 か所**（`excel_report._to_cell_value` と
  `pdf_tools.normalize_char`）にありますが、**用途が違います**——前者は
  「Excel に数値として認識させる」ため、後者は「PDF の文字を突き合わせる」ため。
  同じ関数名で括ると、片方の都合がもう片方を壊します
* **配布物の番人**（`wall_quantity_mapping.json` の `guard`）… 配布物が改訂
  されたら気付くための検査で、ツール固有の資産です
* **面材張り大壁は雛形を持ちません**（PDF をゼロから組み立てる）。
  2.1 の話は最初から関係しません
* **画面固有の振る舞い**… 和暦の組み立て・部屋の見出しの追従・釘配列図の縮尺・
  出力結果の表。これらは 3.1 の部品には入れません

## 5. 順序

**小さく・独立していて・既存のテストが合否を決められるもの**から進めます。
どの段も単独で完結し、途中で止めても中途半端な状態は残りません。

| | やること | 触るもの | 合否 |
| --- | --- | --- | --- |
| **第 1 段** ✅ | **雛形の設定を 1 つにする**（2.1）。`GET /settings` → `GET /template` の形寄せを含む | `portal_sdk` ＋ ツール 2 つ ＋ 証明書の画面 1 か所 | 雛形設定の既存テストが落ちないこと |
| 第 2 段 ✅ | **ファイル名の規則を 1 つにする**（2.2）。画面とサーバが同じ規則であることをテストで縛る | `portal_sdk` ＋ ツール 3 つ ＋ `pdf-file-ops.js` | 既存テスト ＋ 新しい突き合わせのテスト |
| 第 3 段 | **突き合わせの外枠を 1 つにする**（2.3） | `portal_sdk` ＋ ツール 2 つ | 既存の verify のテストが落ちないこと |
| 第 4 段 | **生成物の引き渡しを 1 つにする**（2.5） | `portal_sdk` ＋ ツール 4 つ | URL も応答の形も変わらないこと |
| 第 5 段 | **入力欄を部品にし、デザインシステムからツール固有のクラス名を追い出す**（3.1・3.2） | `src/components/` ＋ `src/styles/components.css` ＋ 画面 3 つ | 既存の画面テスト ＋ デザインシステムのテスト |
| 第 6 段 | **雛形を設定する画面を部品にする**（3.3） | `src/components/` ＋ 画面 2 つ | 既存の画面テスト |
| 第 7 段 | **条件の語彙を 1 つにする**（2.4） | mapping 2 つ ＋ `portal_sdk` ＋ 画面 2 つ | 既存テスト（mapping の書き換えを伴うので最後） |

### 進め方の決めごと

* **1 段ずつ。3 つのツールを同時に書き換えない。** 間違いに気付くのが 3 倍
  遅れます
* **合否は既存のテスト。** どの段も「URL と応答の形が変わらず、既存のテストが
  1 本も落ちない」ことが判定です（第 1 段の `GET /settings` だけが意図した例外）
* **先回りして一般化しない。** 寄せるのは**実際に 2 か所以上で重なっているもの**
  だけで、「将来こうなるかもしれない」を語彙に入れません
* **置き場所は土台（`portal_sdk` と `src/components/`）。** 土台とツールの
  あいだに新しい層を作りません
